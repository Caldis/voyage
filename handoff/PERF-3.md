## 根因（测量坐实，推翻了一半的原假设）

原假设（PERF_REPORT_wave3 §4.3）：钱花在「子射线从半路重走」和「每条子射线完整着色」。

1. **着色几乎不花钱**：把子射线的着色整个换成常数，边缘开销只少 0.01–0.02 ms。「复用中心射线颜色」本身省不了多少。
2. **白走的阴影段（新发现，最大的一笔之一）**：`wingTrace(..., shadowSteps = 0)` 只是把循环总数少算了阴影步数，
   法线算完后阴影段照样跑，直到循环用完（子射线 64·3+4 次里剩下的一百多次），结果再被中心射线的阴影覆盖。
   夜景每个边缘像素子射线合计 174 次迭代里约 70 次是这个。修法：`shadowSteps <= 0` 时法线算完就 `break`。
3. **求交步数与 warp 尾巴**：子射线从命中点前 16 像素出发，贴着表面每步只挪 0.3–0.6 个像素，打中平均 20 步；
   偶尔一条出盒 / 用完要 37–64 步。一个含边缘的 warp 平均有 8 个边缘像素，几乎每个 warp 都有一条长尾，
   **warp 的耗时 = 最慢那条**。所以压平均不够，要压上限。
4. 起点改到 4 像素前、每条限 16 步以后，`route-hnd-cts` / `sunset-wing` 的前缘（压在短舱 / 整流罩上的内轮廓）出现一条亮线：
   内轮廓像素的子射线擦过前缘以后，贴着前缘下表面慢慢远离，16 步（甚至 32 步）走不到后面的部件，这条子样本露出背后的天空。
   调试可视化（子射线结局 / 打中部件染色）确认：不是着色问题，是这几条子射线要四五十步才到后面的部件。

## 改了什么（`wing.glsl.ts`、`wing-shading.glsl.ts`）

- `wingTrace`：记录 `tGraze`（第一次擦过别的部件时最近的那一步）与 `steps`（求交用了几步）；`shadowSteps <= 0` 算完法线就结束；
  新参数 `tJump`：内轮廓像素的子射线擦过前面的部件（离它曾不到 3 像素、已远离 1 像素以上）后，直接跳到中心射线命中点前 4 像素处。
- `wingView`：
  - 子射线起点：外轮廓 = 中心命中点前 4 像素；内轮廓 = 擦边点前 4 像素（原来是命中距离的一半 / 16 像素）。
  - 四条子射线共用 `uWingSteps/2` 步的预算，每条至少给后面的留 8 步（原来每条各 `uWingSteps/2`，外加白走的阴影段）。
  - 边缘像素上中心射线照常着色，颜色只给子样本沿用：同部件且法线差 < 18° 的子样本直接用中心颜色，其余自己着色。
  - 试过「子样本之间也互相复用」：要多开两个数组，寄存器压力让**非边缘像素**也慢了 0.02–0.03 ms（EdgeAA=0 对照测出来的），得不偿失，删了。
- 调试位：128 子射线一律从一半出发（旧起点），256 每条子样本都自己着色，1024 每条子射线各给 `uWingSteps/2` 步（旧预算），4096 内轮廓不跳。

试过又撤掉的：子射线擦过部件后在距离场里「跳过这个部件」（最近部件判断不准，会跳过后面真正要打的部件，亮线更重）；
步数用完仍在逼近的子射线「提升」为打中并沿用中心颜色（前缘冒出亮点）；两者合计也只省 0.01 ms。

## 坑

- **截图之间翼尖姿态在变**：`uWingFlex` 每帧按时间更新，`turbulence = 0` 也还有 0.015 m 的慢摆动，同端口相隔 600 ms 的两张图边缘会错开一个像素。
  1:1 对比要在 `--eval` 里冻结：`Object.defineProperty(window.__voyage.wingMat.uniforms.uWingFlex, 'value', {get(){return 0.5}, set(){}})`。
  冻结后基线 / 本分支两端口的截图机翼逐像素对齐，差异图里只剩云。
- **同一版本前后两次截图也会有零星亮点的差别**（夕阳下云和海面的高光在动，边缘像素的去亮点上限 `refL` 跟着变）：看到一两颗亮点先同版本再拍一次，确认不是算法引起的。
- `wingTrace` 的 `shadowSteps` 不是阴影步数的上限（上限是循环总数），以后给「不要某一段」的调用加参数时要显式 `break`。
- 测「省了多少」要同时看 EdgeAA=0 的对照：在 `wingView` 里多开数组会让所有像素变慢，只看总时间会把这部分算成「边缘还没省够」。

## 开发体验反馈

- 最费时间的是定位「前缘亮线」：肉眼对比被翼尖摆动和云的变化干扰，直到冻结 `uWingFlex`、再加「子射线结局 / 部件」染色调试视图才看清。建议把冻结姿态做成 `__voyage` 的一个开关（例如 `wingDebug.freezeFlex`），脚本就不用 hack `defineProperty`。
- `benchWing` 的墙钟在 GPU 被别的代理占用时完全不可信；timer query + 两页交替（`PERF-3-bench.mjs`）稳定得多，建议并入 `dev-browser.mjs bench`。
- 改机翼着色器后页面热更新重编约 6 s，一轮「改 → 截 5 个场景 + 计时」约 3–4 分钟，可以接受。

## 没做 / 留给下一轮

- `uWingSteps` 128 → 96（性能报告的可选项 ③）：没做，需要核对掠射轮廓。
- in-cloud 机翼 pass 仍 0.70 ms，要再降得动非边缘部分（中心射线平均 37 次迭代）。
- 子射线「步数用完」算没打中的比例从 0.07 升到 0.26–0.43 条 / 边缘像素（多数是外轮廓外侧慢慢远离的，算背景是对的）；截图里没看到退化，审查时可以在贴窗 / 看机翼视角再看一眼外轮廓。
