## 1. 物理

### 1.1 a = b = c = 0.5、3 阶，与出处相符
- Wrenninge 2013 的八度近似要求 a ≤ b；Hillaire 2016（Frostbite）沿用；UE Volumetric Cloud 默认 MultiScattering Contribution / Occlusion / Eccentricity 都是 0.5，八度数最多到 2。改后代码逐阶核对无误：k = 1 时是 (a, b, c) = (0.5, 0.5, 0.5)，k = 2 时是 (0.25, 0.25, 0.25)，单次散射拆出来写后与原来 k = 0 那一项逐项相同。
- 天气宏：`msDecay = stormW > 0.5 ? 0.6 : 0.5` 只写在 `#ifdef CLOUD_WEATHER` 里，默认变体用 `const 0.5`，check:glsl 断言也通过。`stormW > 0.5` 是按样本的硬切换，原来 0.7 / 0.62 的写法就是这样，不算本任务引入。

### 1.2 `CLOUD_MS_ALBEDO = 6` 破坏了注释里说的「守恒结构」
注释写的是「它不改变高阶之间的比例，a ≤ b 的守恒结构不变」，这句不对。守恒约束看的是**绝对权重**：乘 6 以后，高阶的实际权重是 3.0 和 1.5，远大于 b 的衰减。具体算几个点（未计相函数和粉末）：

| od（朝太阳） | 改前高阶合计（6 阶） | 改后 ×6 高阶合计 | 单次 e^−od |
| ---: | ---: | ---: | ---: |
| 0（薄边、薄幕） | 1.48 | **4.5** | 1 |
| 5 | 0.74 | 0.68 | 0.0067 |
| 10 | 0.50 | 0.14 | 4.5e−5 |
| 20（塔身背光、云里深处） | 0.33 | **0.010** | ≈0 |

- 所以研究报告和注释里「od = 5 处高阶是单次散射的约 100 倍，背光面被灌满」这个解释不成立：改后 od = 5 处**仍然**约是单次散射的 100 倍（0.68 / 0.0067）。对比度真正来自曲线的**斜率**：改前 od 0 → 5 只降到 1/2，高阶尾巴（b^k → 0 的第 3–5 阶）几乎是一个常数环境光；改后 od 0 → 5 降到约 1/6.7。README 坑点和 clouds.ts 注释要改成这个说法。
- 薄的一端：od → 0 时高阶源项是单次散射的 4.5 ×（粉末 0.70–1）≈ 3–4.5 倍，顺光时比改前大约 2.4 倍。光学上薄的东西（薄幕、卷云、碎云边）物理上几乎只有单次散射。这次 cirrus-noon 只亮了 +4/255，看不出发光，暂不要求改，但需要在 README 里记下这是一个已知的非守恒增益。
- 厚的一端（R1 / R2 的根因）：三阶都是指数衰减，od ≳ 10 时全部归零，背光面和云里只剩天空环境光（蓝色）。真实的厚云在深处属于扩散区，漫射光按 ≈ 1/(1 + 0.75(1 − g)τ) 慢慢衰减（仓库里 `keyVisibility` 已经在用这个二流近似，τ = 20 时还有约 0.31）。塔身于是变成深蓝剪影。在云里时，每个样本的受光几乎全靠 `1.5·e^{−0.25 od}` 这一项；它对受光步进（T32 随机平铺细节）估出来的 od 极其敏感，逐像素的方差被放大，最后以棋盘纹的形式留在重建结果里。

### 1.3 「把能量归一化写进公式」的更守恒写法（建议修法，已验证方向）
与其用一个与 od 无关的魔数，不如给多次散射加一个**扩散尾巴**，用二流近似里已被散射、没被吸收的那一份：

```glsl
// 审查用变体（C01rev-tail.mjs，K = 1）：加在 `vec3 sunLight = keyLight(r, up) * sunScatter;` 之前
sunScatter += K * (1.0 / (4.0 * M_PI)) * (1.0 / (1.0 + 0.1125 * od) - exp(-od));
```

这个量有物理意义，上界是 1；od = 0 时为 0，粉末式的「薄边还没攒起来」自然就有了；到深处慢慢衰减，和 `keyVisibility` 用的是同一个式子。同页冻结、真平均 64 帧（`tmp/screenshot/c01rev/tail/`）的结果：

| 场景 | 指标 | 分支 new | +tail K=1 | +tail K=2 | master |
| --- | --- | ---: | ---: | ---: | ---: |
| in-cloud | 棋盘纹（相邻像素差） | 12.9 | **6.5** | 4.9 | 7.5（实时） |
| | 雾的 RGB | 186/186/189（偏蓝） | 190/188/187（中性） | 198/196/193 | 190/188/188 |
| typhoon-bands | 观感 | 深蓝剪影 | **灰蓝，有体积** | 更灰 | —— |
| clouds-variety | 窗均值 / p99 | 139 / 202 | 143 / 202 | 146 / 203 | —— |

代价：clouds-variety 的云芯对比会略降（尾巴把背光面抬了一点，目测降幅不到一成）。建议返工的具体做法：
1. 在公共主体里加上这条尾巴（K ≈ 1），把 `CLOUD_MS_ALBEDO` 往下调，使受光云顶的 πL/E p90 仍约 0.75（用 `C01-albedo.py` 复标）；
2. 重测 int_rng / int_c，clouds-variety 相对当前 new 的降幅不超过约 10%；
3. in-cloud 的相邻像素差回到 master 水平（≤ 8）；typhoon-bands 和 storm-day 的塔身再请美术看一次。

如果尾巴只想给天气用，也可以放进 `#ifdef CLOUD_WEATHER`，但 R1 在晴天层状云里同样存在，所以**至少晴天也要处理云里的情况**。

### 1.4 粉末只压高阶
这个解释（刚进云的薄层里多次散射还没攒起来）合理，也和 Nubis 的「dark edges」思路一致。但 Schneider 2015 的原文是经验性的，并没有「只压高阶」这一说，注释里别写成「Schneider 2015 的物理解释」，改成「按其物理含义的解读」。加了 1.3 的尾巴以后，薄边的衰减由公式本身提供，粉末可以保持现状。

## 2. 曝光锚定（C02）——通过

- 公式 `eO = mix(eO, max(eO, log2(1000/1.2) − EV), day·y)`：场景单位是 kcd/m²，log2(1000/1.2) − 15 = −5.30，按 Lagarde 的 EV100 定义，单位核对无误。因为是 `max`，它**只会抬高、不会压低**曝光。只有自动曝光低于 −5.30 时才会生效，折算下来窗外对数均值要高于约 7 kcd/m²（log2 kcd > 2.83），这只有受光的云海或雪原能达到。
- 各种情形逐一核对：
  - 黄昏、夜间：`day` 门控，亮度也远够不到锚点；
  - 雷暴暗云：对数均值低，锚点不起作用；
  - 云里：in-cloud 的 o = 1.6，锚点不起作用，靠的是 ⑤；
  - 开灯舱内（④' 的 lit）：夜间 `day = 0`；白天窗外很亮时 dom ≈ 0；
  - 睡眠档（白天）：舱壁随 ③ ④ 的上限一起变亮，clouds-variety 139 → 148，是朝 T23 的 150–185 靠拢，可以接受。
- ⑦ 倒影增益：锚定后 clouds-variety 和 in-cloud 的 `adapted.w` 仍然是 0（meta.json），白天没有触发，「白天 eO ≤ eC」依然成立。⑧ 的上限按 eC − eO 相对计算，显示比例不变。T47 按曝光倒数混合，本来就是凸组合，与 eO 的取值无关，不会过冲。
- `EXPOSURE_WHITEOUT` 的契约：`keyVisibility` 在 main.ts 里每帧都调用（481 行），用的数据源是 T31 同一个 `immersed`（也来自同一个密度探针），和 T31 的穿云光斑一致。T46 夜云由 `day` 门控，一致。三个 pass 共享同一个 uniform 对象；即使写入时机相差一帧，也可以忽略。这里不要求改动。
- 小建议（不阻塞）：现在锚点以上完全不再自适应，是一个硬 max。「有限自适应」可以写成软膝，例如超出锚点的部分只抵消 30–50%，雪原 + 云海的极亮窗就不会一路推进 AgX 肩部。留给 TM 任务一起做。

- **clouds-variety / cu-side**：明显进步。云更白、背光的「菜花」读得出来，缝里的海更深。没有过曝（截白 ≤ 0.01%），也没有脏灰。**新问题**：中景掠射的水平横纹（梳齿）因为对比变高而更显眼了（放大图里 y ≈ 700–800 一带）。这是 C03 的范围，交接已写，C03 要优先排。
- **backlit-cu**：云缝更深、云更立体，太阳附近没有过曝，可以接受。
- **sunset-wing**：几乎不变，略好。
- **cirrus-noon**：略亮，看不出发光，通过。
- **in-cloud**：见 R1，**不通过**。
- **typhoon-bands / storm-day**：塔顶和砧顶更亮是好的，但背光塔身是深蓝剪影（R2），**不可接受**。真实的积雨云背光面是灰到灰蓝，里面有扩散出来的光，不会是墨蓝；按 1.3 加尾巴后就是这个方向。

### 对交接里「还不够好」两点的判断

**(i) AgX 高光段把显示对比压掉约三成**：判断属实。HDR ×1.7 到显示 ×1.4，正是 AgX（three 默认 base）肩部偏缓造成的。建议另开任务「TM01 窗外高光段对比」：
- 方向一：在 AgX 前加一个只作用于窗外像素、按 `day` 门控的 look。参考 Blender AgX「Punchy」：log 域 slope 约 1.1–1.2 或 power 约 1.3–1.35，饱和度要单独控制，不要一起拉高。
- 方向二：给窗外试 Khronos PBR Neutral，它在 0.8 以下几乎是线性，对白云的高光层次更友好。
- 验收：满窗云场景的「显示 / HDR 云芯对比比」从约 0.8 提到 ≥ 0.9；舱内不变（舱内色调用的是 T28 的色适应，不能跟着改）；黄昏和夜景逐像素不变。
- 同一个任务里可以把 C02 的硬 max 改成软膝。

**(ii) 逆光银边没有变亮**：交接说 HDR 里的 rim 也只有 1.16，所以这不是色调映射的问题，而是光照或几何的问题。我的根因推测：
1. backlit-cu 里云与太阳的夹角大多在 20–40°，`hg(0.9)` 的衍射峰在 10° 外就迅速衰减。真实的银边只出现在太阳几乎正在云后（< 5–10°）的地方，现在的场景根本拍不到；
2. rim 指标取的是不透明度 0.2–0.8 的像素，这些像素的亮度混着身后的背景（近太阳的天空本来就很亮），比值被拉平；
3. 受光步进从 60 m 起步，前 3 步带细节，薄边朝太阳的 od 可能被高估。

建议任务「C09 逆光银边」：先做一个「太阳在积云正后方 3–8°」的场景，从云缓冲读 HDR rim（不看截图）；再对照「前向峰加一个 g ≈ 0.6 的宽瓣」和「受光步进首步缩短到 20–30 m」两个变体。

## 开发体验反馈
- **有用**：`C01-measure.mjs` 加 `--vfile` 的同页 A/B 很顺手，我加一个 3 行的变体文件就把修法验证了；meta.json 里带着适应结果，查曝光判据很方便。`dev-browser flicker --crop` 可以直接量棋盘纹的时间稳定性。
- **坑 1**：实现者的回归表只量了 luma 均值，所以 in-cloud「188 → 186 恢复」掩盖了棋盘纹和色偏。建议给 `compare.mjs --measure` 加两个输出：区域的**相邻像素差**（高频 / 棋盘）和 **RGB 均值**（色偏）。这两项在本次审查里都是一眼能看出、均值量不出来的回归。
- **坑 2**：`final/in-cloud/new.png` 是 whiteout 修复前拍的（141），`final3` 才是 186，目录名看不出先后。建议交接表里每一行写明来自哪个目录。
- **坑 3**：`dev-browser shots` 在冷启动下没等天气变体编好就拍了（typhoon-bands 拍成晴天），也没有报警。建议 shots 等 `wantedKey === marchShown` 以后再截图，或者在 JSON 里输出实际画的变体。
- **坑 4**：清理 worktree 时 cmd 的 `rmdir` 删不掉 pnpm 的 node_modules，因为它们是实目录，只有里面的包目录才是联接。用 PowerShell 按 ReparsePoint 先删联接再删目录，这个办法可以写进 SOP 的清理步骤。
