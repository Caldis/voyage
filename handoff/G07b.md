两轮合计：水体仍是 GPU 画布的做法 16 个窗口（16 分钟）里 waterRead 段 26 个尖峰（1.6 / 分），CPU 水体 8 个窗口里 0 个（按同一速率期望约 13 个）。read 段两轮合计：GPU 水体 21 个 / 16 分钟，CPU 水体 8 个 / 8 分钟，同量级——水体一项不影响 read 段，read 段仍是剩下的主要来源（约 1 / 分）。
**审查所说「G07 比 G06 多约 1.7 倍」这次没复现**：同页交替 G06 17 对 G07 12（审查三轮合计 20 对 34），两者都是同样两类读回尖峰，差异在计数噪声内；本任务不认为 G07 引入了新的尖峰来源。
原始数据：`tmp/screenshot/G07b/spikes-1.{txt,json}`、`spikes-2.{txt,json}`。

归因要点：
- Worker 各阶段中位时刻（离任务开始）：read 23–25 ms、water 26–33、waterRead 41–47、night 112、roads 350–490、mips 420–550。尖峰**只**出现在 read 与 waterRead 两段——都是对 GPU 资源的同步读回（主线程 GPU 加速画布拼好的影像位图 → `drawImage` + `getImageData`；水体 GPU 画布 → `getImageData`）。
- read 段的尖峰全部出现在「这次读回比平时慢一倍」的任务里（readMs 43–68 对中位 23–25），也就是 GPU 进程那一刻忙、读回排队，页面的合成 / WebGL 命令排在它后面，帧跟着卡 3–5 个 vsync。
- mip 阶段 0 个尖峰、有上传的帧附近 0 个（只有 1 个在背靠背任务里、同帧上传 1.8 ms），**mip 临时缓冲的 GC 假设不成立**：复用缓冲后 mip 阶段本来就没有尖峰，G07 14 对 G07b 9 的差全在 read 段（7 对 2），机理上与 mip 无关，计数也小（泊松噪声量级），不能当作复用的收益。复用本身逐字节相同、离线 GC 次数 22 → 8，留着无害。
- 水体改 CPU 栅格后 waterRead 段 11 → 0（G07 + G07b 8 个窗口 11 个，cpuWater 4 个窗口 0 个；按零假设期望约 5.5 个，P(0) ≈ 0.4%）。water 阶段多约 5 ms（CPU 栅格，在 Worker 里，不碍主线程）。
- 影像画布也改 CPU（`imageryCanvasCpu`）试过：read 段 24 → 10 ms，但主线程每次建级出现约 59 ms 长任务，20 s 里 11 个尖峰（33 / 分），**否决**，开关留作对照、默认 false。

证据强度：水体一项「强」（机理清楚、阶段定位精确、两轮同页交替 26 → 0，期望约 13）；read 一项「定位清楚、未修」；「G07 比 G06 多」一项「未复现」（见确认轮）。

## 还没做 / 已知问题

- **read 段尖峰（每分钟约 1 个）的根治**：把瓦片拼接整个挪进 Worker——主线程把本级瓦片的 ImageBitmap（`createImageBitmap(blob)` 解码的，CPU 侧）连同目标矩形 `postMessage` **克隆**（不转移，LRU 还要用）过去，Worker 在 `willReadFrequently` 的 CPU 画布上 `drawImage`，读回就是内存拷贝；细节层（GSI）的限时逻辑（`DETAIL_WAIT_MS`）要改成「到点把已到的瓦片发过去」。画面会有一次与本次水体同类的重采样差异（CPU 与 GPU 的高质量缩放不同，`fine = false` 时 2× 放大尤甚），需要同页 A/B 看最大差。改动集中在 `clipmap.ts` 的 `buildImagery` / `buildDetail` 与 `road-raster.ts`，建议另开任务。
- 水体 CPU 栅格在 ANGLE Metal / Safari 上没测（Mac 上 GPU 读回的代价可能更大，这一项的收益可能更明显；CPU 栅格耗时在 M 芯片上应不成问题）。
- G07 审查 L4（PBO 在 Metal 上未实测）、L5（首载 8 s 内跨黄昏阈值）照旧，未处理。
- `G07-tier.mjs` 是 G07 的行为（手动画质档决定地面精度），已过时，用 `G07b-panel.mjs`。
