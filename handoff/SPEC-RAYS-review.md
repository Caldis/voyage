## 结论：返工（只有一项必须修，其余都是建议）

架构方向和接线都对，性能在预算内，光条本身也稳。比较下来，A 方案（体积查云影）确实比径向模糊更真实，也跟所在大气用的是同一套物理量。云下低空（rays-gap-low）改完明显更真实：以前整块云底下是发光的橙褐色霾，现在云底暗、云缝亮。
**返工的理由只有一条：步进时不知道地形在哪（下面 P1）。** 火车模式和低空山地里，前景地面被错误地减掉整条视线到海平面这一路的空气散射，画面大面积压暗、发艳。这一条修好后，协调者核验就能合并，不需要再审一轮。

## 问题（按严重度）

### P1（必须修）：步进终点是海平面球面，地形、奇观等不透明物体后面的空气也被减掉

- 代码：`rays.ts` MARCH_FRAG 用 `tGround = raySphere(o, rdW, BOTTOM)` 当终点，没有考虑地形高度（`uGroundOn` / `uTerrainMax` / `groundHeightAt`）。视线打到 0.5 km 外的草地，步进还是一路走到海平面，最远走 400 km，把山体或地面背后那段本来就没画进画面的空气散射，也当成「云影里的 ΔL」减掉了。合成 pass 最多减到 90%，这个上限恰好就是地面被压暗的幅度。
- 实测（冻结同机位，a = 开，b = 关，`raysrev-diff.py`）：
  | 场景 | 变化像素 | 亮度差均值 | 最小 | 变暗 > 10 级的像素 |
  | --- | --- | --- | --- | --- |
  | rv-rail-afternoon（火车，大糸线 12.65 km，8/5 17:30，覆盖率 0.55） | 50.4% | **−14.5** | **−88** | **43.3%** |
  | rv-fuji-low（富士，2 km，16:30，覆盖率 0.5） | 14.9% | −0.3 | −10 | 0 |
  | rv-floatcity-day（浮空城，云海 0.6） | 8.3% | −0.6 | −35（在海面缝里，城体本身没变） | 2.5% |
  | rv-jianmu-day | 13.8% | −0.04 | −9 | 0 |
  火车那张（`rv-rail-afternoon.tri.png`，从左到右是开 / 关 / 差异）：前景草地整块从灰绿变成饱和深绿，差异热图从窗底到远山一片红，而窗底的草离相机只有一两百米。远山也被「去霾」变蓝。粗看像是更通透了，其实是减错了：近处空气只有几百米，根本没有那么多内散射可减，这违反「由近到远、近处是起点」这条铁律。
- 修法（建议）：
  1. 在步进循环里加地形终止：`uGroundOn > 0.5 && h < uTerrainMax` 时查一次 `groundHeightAt`（ground.glsl.ts，窗外程序在用的同一个高度场），p 落到地面以下就停，最后一步按比例截断。rays 本来就不在冷启动关键路径上，代价是 48 步里低空那几步各多一次查表（1/4 分辨率上）。
  2. 火车模式或贴地时，山脊线和天空交界处会有 1/4 分辨率加 4×4 模糊造成的 ΔL 渗边（约 16 px 宽的光晕）。修完第 1 条后拍一张火车 / 富士低空的山脊特写。如果看得出，就在合成里用全分辨率的「是否地形」（例如 hdrOutside 的某个已有信号，或者步进时顺手输出的地形标记）挡一下，或者上采样时按 ΔL 差异加权。
  3. 奇观、远处飞机这类不透明物体也属于同一类问题（它们后面的空气也被减了）。实测浮空城、建木的城体上看不出来，天梯在 −4° 以下时 rays 已经关掉，可以先不管，但要在 README 坑点「没管到」里写一句。
- 验收：`rv-rail-afternoon` 开 / 关的前景草地（窗下半部）亮度差 ≤ 2 级；远山的差异只剩真实的云影空气那一部分；sunset-wing 和 backlit-close 的结果不变。复现用的 json、js 和 py 在 `tmp/screenshot/SPEC-RAYS-review/`，命令是 `shots --freeze`（pair 模式）`--scenes-file raysrev-occl.json --pair "$(cat raysrev-on.js)" --pair "$(cat raysrev-off.js)"`。

### P3（建议，美术）：backlit-close 的海面偏饱和深蓝，影墙交界带偏淡紫

- 作者最终截图 `final/backlit-close.png` 的右半边，在窗中线取样：暖霾（253,243,228）→ 交界带（122,117,139）偏淡紫 → 海面（96,124,140）→ 窗底（33,60,87）是深海军蓝。真实照片里低太阳、云影下的逆光海面一般是灰蓝或钢蓝，饱和度远低于这里。偏色主要来自舱内色适应：画面被暖色霾主导，白平衡往暖偏，把已经偏蓝的影子区域又推高了一截（作者在坑二里也写了这个机制）。
- 不挡合并。建议下一轮美术总监来定：先试 `uRaysGain = 0.8`，或者只减 Rayleigh 加 Mie、霾项减一半，看交界带的紫是否退掉。rays-gap-low 的改善很明显，不能为了这一张把效果整体收掉。

### P3（建议）：出现和消失是硬切

- 编译完成的那一帧（开机后约 0.4 s，`want && frames > 2`），以及 `wanted` 翻转时（云覆盖率从 0 变正、云影图重建），整窗会跳一下：sunset-wing 平均约 2 级，火车模式修 P1 之前是 14 级。建议 ΔL 增益在 0.5 s 内从 0 淡入（一个 uniform，不影响「不画时逐位不变」）。
- **已排除的疑点**：太阳 −4° 那一刀（和主光源换成月亮用同一个门限）没问题。实测 −2.07° 时差异最大 8 级、−2.93° 时 6 级、−3.37° 时 2 级，到 −4° 时 ΔL 已经趋近 0，看不出跳变。

### P4（记录）：显存

- `rays.target` 是全分辨率 RGBA32F（跟 hdrOutside 同一种类型，因为太阳辐亮度需要 float32），在 3840×1950 下约 120 MB。第 60 帧起不管白天黑夜都会分配（`prepare()` 编译时就绑定并分配了它）。可以接受，但建议在 README 的显存账里记一笔。

## 物理与数学

- 单次散射积分 `T·S·(1−stepT)/ext` 是标准的解析步长（Hillaire）。相机在云顶以上时，T 用两段 `transmittanceToTop` 相除，推导正确（相机在从 pA 出发、沿 −rd 通往大气顶的路径上）。
- 起点按 Bayer 4×4 错开，再做 4×4 盒式模糊，覆盖是完整的。模糊结果偏半个纹素，合成时 `uv − 0.5/uRaysRes` 反向挪回，算过一遍是对的。
- 三通道共用一个 k、最多减 90%：这是合理的保险（逐通道夹会出紫点，作者有记录）。但 P1 说明，当前 90% 的上限在掩盖一个几何错误，并不只是在吸收积分误差。修完 P1 后，建议统计一下 k < 1 的像素占比：正常应该接近 0。
- 只减单次散射、保留多次散射（天光），暗条就是灰蓝色，这符合真实观测。

## 开发体验反馈

- `dev-browser.mjs shots --only` 认不出 `--scenes-file` 里的场景名，报「未知场景」。我去掉 `--only` 后正常了。建议让 `--only` 也能匹配 `--scenes-file` 和 `--scene` 里的名字，或者至少在报错里提示一句。
- 共享测量锁排队很长（这次 shots 前面有 3 个 gpu-ab 在等，等了约 6 分钟）。截图类的 shots 其实不需要等 GPU 计时锁，建议 `--respect-lock` 分成「计时」和「只截图」两档。
- 地面瓦片（EOX）在 headless 里持续报 CORS / ERR_FAILED，一次截图约 600 条。已经聚合了，不算 error，但这时低空地面画面其实是缺影像的，建议汇总行里标一句「地面影像缺失，地面画面不代表真实观感」。
- 作者交接写得清楚：坑四（`probe --read` 的读回坐标是左下原点）这种记录很有价值，建议协调者把它改进 probe.mjs 的文件头注释。
