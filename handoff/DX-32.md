# DX-32：`dev-browser.mjs --wait-quiet` 同时检查 GPU

worktree `agent-a7337d73d94b03704`，开发端口 5306。

## 背景

PUB-3 / PERF-16 的帧时间被一个没关的浏览器页面占 GPU 约 51% 污染，而 `--wait-quiet` 以前只看 CPU（DEV_SOP.md「测量前查 GPU」一条、`handoff/PERF-16.md`、`handoff/PERF-16b.md`）。这个任务把 GPU 利用率检查补进 `--wait-quiet`，并让常用的测量工具把「测量开始时 GPU 忙不忙」记进结果里，方便事后复盘一次异常数字是不是被 GPU 负载污染的。

## 设计要点（接手必读）

- **为什么要连续两次采样才算空闲**：GPU 利用率单次采样噪声大，一帧的活可能恰好落在两次 `nvidia-smi` 采样的间隙里，单次采到 0% 不代表真的空闲。两次都 <= 阈值才 break，任何一次超阈值就把计数清零重来。
- **CPU 段和 GPU 段是两个独立的超时**（各自默认 5 分钟），CPU 先等完（或超时）才开始等 GPU，不是两边并发轮询——这样日志顺序好读（先看 CPU 稳没稳，再看 GPU）。
- **`sampleGpuLoad` 用 `execFileSync` 同步调用 `nvidia-smi`**，和 `sampleCpuLoad` 用 `powershell Get-Counter` 同一个模式（都是「拿一次当前值，几百毫秒内返回」，不是长驻监控）。没有 `nvidia-smi` 时 `execFileSync` 直接抛异常，`catch` 里返回 `null` 并打印一次性的环境提示（用一个模块级 `let warnedNoNvidiaSmi` 去重，不然 `bench` 每个场景采一次会刷屏）。
- **`gpu-ab` 的默认检查和 `--wait-quiet` 是两回事**：默认检查只是「采一次、超阈值就警告」（`sampleAndWarnGpu`，不阻塞），`--wait-quiet` 才是「真的等到空闲再开始」（`waitForQuiet`，会阻塞轮询）。`gpu-ab` 本来就有自己的一套负载感知（`sampleAndWarn` 记 CPU 的 `load0`/`load1`），这次照着同一个模式加了 `gpuLoad0`/`gpuLoad1`，字段名和打印格式跟现有的 CPU 版本对称，接手的人不用重新学一套。
- **`bench` 的 `GPU占用=` 和 `gpu=` 是两个不同维度**：`gpu=` 是已有的 `EXT_disjoint_timer_query_webgl2` 结果（这次渲染这一帧 GPU 花了几毫秒），`GPU占用=`（`gpuLoadPercent`）是这次 DX-32 新加的、`nvidia-smi` 报的整卡利用率百分比（这次渲染开始时 GPU 有多忙，可能是别的进程占的）。两个都留着，别在文档里混成一个东西。
- **`--out` / `--jobs` 都相对仓库根解析**（不是 `apps/voyage`，也不是当前目录）——验收时踩了一次这个坑（README 里其实已经写明了，只是又忘了一次），传路径记得从仓库根算，或者干脆传绝对路径。

## 验收记录

开发端口 5306，`pnpm typecheck`、`pnpm check:glsl` 均通过。

1. **空闲时 `bench --wait-quiet` 不额外等待**：GPU 本机空闲（`nvidia-smi` 报 0~1%），跑 `node scripts/dev-browser.mjs bench --port 5306 --only noon-cumulus --wait-quiet --rounds 2`，只在「差一次连续采样」时打印过一次等待提示，几秒内测完，输出带 `gpuLoadPercent` 字段（这次测量本身开浏览器渲染会把 GPU 从 0% 带到 30~40%，这是真实负载，不是误报）。
2. **人为制造 GPU 负载时会等待并打印原因**：另开一个 `dev-browser` 私有浏览器进程（读同一个 5306 页面），用 `window.__voyage.benchFrame(60)` 在一个循环里连续渲染 3 分钟，`nvidia-smi` 确认 GPU 到 91~100%；此时跑 `bench --wait-quiet` 反复打印 `[--wait-quiet] GPU 93%/100%/96% > 10%（需连续两次 <= 10% 才算空闲）...`，持续等待不推进。
3. **负载撤掉后继续**：只按负载进程自己启动时拿到的 PID `taskkill /PID <pid> /T /F` 关掉（不按端口反查），`nvidia-smi` 确认回到 0%，再跑同一条 `bench --wait-quiet` 命令，正常测完并给出结果。
4. **`gpu-ab` 输出里有 GPU 利用率字段**：跑一个最小 smoke job（两个不改材质的变体，`--rounds 3 --n 8`），控制台打印 `CPU 24% → 23%；GPU 39% → 39%`，`summary.json` 里每个 job 带 `"gpu": [39, 39]`。
5. **`gpu-ab` 默认检查不阻塞**：不传 `--wait-quiet` 时同样打印一次 `GPU=N%`（在 `gpu-ab --angle=... GL_RENDERER = ...` 那一行），不等待，直接开始测。

验收期间还观察到一次和本任务无关的偶发现象：机器上有其他 Chrome 进程活动时，`bench` 连续跑了几次 `page.evaluate: Target crashed`（GPU 争用导致渲染进程崩溃，`dev-browser.mjs` main() 里已有一条注释提到过这个已知情况），等负载消退后同一条命令又稳定跑通，与 `--wait-quiet` 的实现无关（不带 `--wait-quiet` 的普通 `bench` 也在同一时段稳定成功过）。

## 开发体验反馈

- `sampleCpuLoad` / `sampleGpuLoad` 两个「采一次当前负载」的函数已经很像了，如果以后再加第三种负载源（比如显存占用、磁盘 IO），值得抽一个通用的 `sampleLoad(cmd, args, parse)` 出来，现在先各写一份是因为两者的失败模式和打印文案不完全一样（GPU 没有 `nvidia-smi` 是「正常情况，静默跳过」，CPU 在非 Windows 上也是同样处理，两者其实已经对称，只是没有共享代码）。
- `--wait-quiet` 现在同时管 CPU 和 GPU，函数体变长了不少；如果以后还要加第三个维度，建议拆成 `waitForCpuQuiet` / `waitForGpuQuiet` 两个小函数，`waitForQuiet` 只做编排，现在为了改动最小没有拆。
- 验收时最费时间的不是写代码，是稳定制造一个能被 `nvidia-smi` 测到的 GPU 负载——一开始试了几种轻量场景，GPU 利用率都不够稳定超过阈值；最后用 `benchFrame(60)` 在一个 3 分钟的 while 循环里连续压满才稳定复现到 90%+。如果以后还要写类似的验收脚本，`benchFrame` 配合循环调用是比截图 / `cold` 更可靠的「持续吃 GPU」手法（截图之间有 IO 等待，GPU 占用会掉下来）。
