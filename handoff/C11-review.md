## 问题（按严重度）

### 低 1：`uReset` 那一帧直接输出原始 cur，云里重置后约 0.3 s 会闪回旧的棋盘纹

`if (uReset || …) { gl_FragColor = cur; return; }` 在 3×3 循环之前就返回了，重置帧写进去的是没平均的原始值。之后历史按 blend 0.12 收敛，残留大约按 0.88ⁿ 衰减，10 帧后还剩 28%，20 帧后剩 8%。触发重置的有 `snap()`：换预设、`setSize`（窗口缩放、**自动画质档切换**也会走 resize）、`setParams(…, false)`。在云里碰上这些，整窗会先闪一下老样子的棋盘纹，然后才变干净。按铁律，闪烁的优先级最高；不过这里触发少、持续短，所以定为低。
**修法**：把邻域循环挪到 reset 判断前面（reset 很少发生，多读 9 次无所谓），左半在 reset 分支里也输出 `mix(cur, nsum/9, w)`；或者只把左半的 reset 分支改成走循环后再返回。

### 低 2：云外的逐位不变依赖「邻域没有 NaN / Inf」

权重为 0 时 `mix(cur, nsum/9, 0.0)` 在 IEEE 下等于 `cur·1 + x·0`。邻域里只要有一个 NaN 或 Inf，`x·0` 就是 NaN，云外也会把 NaN 扩散到 3×3。改动前 NaN 只留在它自己那个像素，邻域夹取里 HLSL 的 min/max 会把它吃掉。raw 写出前有 `min(L, 60000)`，这次在 7 个场景的整张缓冲上实测 NaN 为 0，所以现在不是问题，只是这个保证比较脆。
**修法**（零成本）：`float wImm = clamp(…); if (!depthHalf && wImm > 0.0) cur = mix(…, wImm);`。冷编译实测 67 → 66 ms，在噪声以内（见第 4 节）。这样云外的逐位不变也不再依赖编译器怎么展开 `mix`。

### 低 3（观感，可选）：半在云里时只降了一部分

权重对 imm 是线性的。飞在云底或积云边缘（imm 0.1–0.5）时，雾里那层斜纹只减了一点。partial_sc（imm 0.22，1.1 km 层积云底，下面能看到海）的云区裁剪：adj 1.15 → 0.95，对角高频 0.37 → 0.30。这些状态本身的噪声比深处低（深处 old adj 2.6–4.9），正常显示下看不太出来，所以不算缺陷。想更彻底的话，可以把权重改成 `smoothstep(0.02, 0.3, imm)` 这类更陡的曲线；代价是出云后的 1–2 s 里，远处云的边会多糊一点（高档是 3 屏幕像素，低档是 6）。建议交给美术总监按观感定，本任务不必做。

### 已核实、不成问题的点

1. **纹素一致性 / 双宽缓冲边界**：`uCurrent` / `uCurrentDepth` 是 raw（w×h，**不是**双宽），`q = clamp(ip + d, 0, hi)`，其中 `hi = uCloudResolution − 1`。求和读到的正是夹取已经读过的那 9 个纹素。左半最右一列的邻域夹在 raw 的 w−1，**读不到**右半的深度数据；屏幕边缘同样夹到边上。`setSize` 在每次换画质档时同步 `uCloudResolution`，0.75 / 0.5 档下坐标一致。实测低档（1600×600 双宽）逐位对照与高档结论相同。
2. **颜色 / 深度一致性**：只平均左半。右半存的是 `(D·α, α)`，`cloudBufferDepth` 取比值，与左半 α 的尺度无关；`cloudBeforeGround` 用的是「左半（已平均）颜色 + 右半深度」，in-cloud 场景下 `depthOn = true`。平均后的 cur 每个通道都落在 `[mn, mx]` 里，与历史夹取也一致。重投影用的 `dCur` 没被平均。partial_sc 的云 / 海交界处，16 帧平均图逐行剖面 new − old 在 ±0.012 /255 以内，没有亮边或暗边（`tmp/screenshot/c11rev/partial/partial_sc_horizon.png`）。
3. **「左半只有云，跨不过机翼 / 地面边」这个说法成立**：步进区间只来自 `cloudShellIntervalH`（云壳、与地球求交决定是否返回空区间），外加 `AERIAL_MAX_DISTANCE`，不按地形、机翼或场景深度截断。地面由窗外 pass 按右半深度和左半 α 合成，机翼由机翼 pass 盖上去（它的雾色取机翼背后的云缓冲）。左半里唯一的「几何边」是窗板外 0.02 那圈 (0,0,0,1)（在窗框后面，看不到），以及云底球面切线处的路程跳变（云里本来就是满窗的雾）。实测：ic_-10_-5 和 ic_10_15 的三个机翼放大区里，平均图差在边缘像素上的 |d| 均值是 0.24–0.80，非边缘是 0.24–0.99，边缘没有更集中，也没有带符号的偏移（+0.03 到 +0.30，与整块云区的偏移相同）。×8 差图上沿机翼轮廓看不到线（`tmp/screenshot/c11rev/ic_-10_-5_zoom.png`，每行依次是 old 单帧 | old 平均 | new 单帧 | new 平均 | 差 ×8）。
4. **出 / 入云没有跳变**：权重 `clamp(imm·1.0204 − 0.0204)` 对 imm 连续。逐位对照里，imm = 0.0199 时逐位为 0，0.02 时最大差 2.8e-4，0.0205 时 1.8e-2，0.03 时 0.34，是线性上升的。whiteout 按 0.5 s 指数衰减，出云后大约 2 s 权重归零（0.5·ln 50 = 1.96 s，与注释一致）。
5. **机翼边上 2 px 的阶梯和点阵是改动前就有的**：old 的 16 帧平均图里，襟翼滑轨整流罩下面同样有点阵阴影（ic_-10_-5_zoom.png 第 1 行第 2 列与第 4 列一样），不是 C11 引入的。C11 只是把盖住它的云噪声去掉了。看板上已经派了 W-STAIR，同意。

## 证据

### 1. 零回归：同一组输入、两个程序各画一次，逐位比较（`c11rev-exact.mjs`）

做法：场景稳定后全冻结（云不再画，raw 和 history 都不动），在同一个 `page.evaluate` 里用 C11 的 resolve 和「删掉那 3 行」的 resolve（= master）分别对同一个 `uCurrent` / `uHistory` 画进两张临时目标，读回整张双宽缓冲逐位比较，再改 `uCloudImmersion` 重画。这样两边的输入完全相同，不受 rAF、云影图分片或冻结时刻的影响。

| 场景 | 实际 imm | imm = 实际值：左半 / 右半 | imm = 0 | imm = 0.0199 | old 重画两次 |
| --- | --- | --- | --- | --- | --- |
| clouds-variety | 0 | **逐位 0 / 0** | 0 / 0 | 0 / 0 | 0 |
| noon-cumulus | 0 | **0 / 0** | 0 / 0 | 0 / 0 | 0 |
| sunset-wing | 0 | **0 / 0** | 0 / 0 | 0 / 0 | 0 |
| cloudbase_1.02（云底下方） | 0 | **0 / 0** | 0 / 0 | 0 / 0 | 0 |
| ic_-10_-5 | 1 | 左半最大 33.7、均值 0.85 / 右半 0 | 0 / 0 | 0 / 0 | 0 |
| ic_-10_-5（**低档** 0.5） | 1 | 左半最大 31.8 / 右半 0 | 0 / 0 | 0 / 0 | 0 |
| ic_10_15 | 1 | 左半最大 39 / 右半 0 | 0 / 0 | 0 / 0 | 0 |
| partial_cu_a / partial_cu_b / partial_sc | 0.52 / 0.08 / 0.22 | 左半有差 / 右半 0 | 0 / 0 | 0 / 0 | 0 |

全部场景都没有 NaN。**云外逐位不变成立。** 右半在任何 imm 下都逐位不变。

**实现者「clouds-variety det.png 两轮都没拿到差为 0 的一对」是测量问题，不是着色器的差异。** 我推测的原因（未单独验证）：`C11-ab.mjs` 的确定性循环在一个 evaluate 里结束，`__c11freeze()` 全冻结又是另一个 evaluate。两次调用之间页面还处在 cloudLive 状态，会插进 0–N 个真实 rAF 帧，每帧推进 `uFrame` 并做一次累积，所以 det.png 是「160 + 若干帧」后的缓冲，帧数随机。另外，每次 `clouds.render` 都会推进云影图和占据网格的分片重建，变体之前那 6 个 rAF 帧的数量也不固定，这能解释「偶尔某一个变体整体差一截、同源的 old / old2 之间也会出现」。

### 3. 冷编译（`shader-budget --variants`，cloud-resolve，7 轮，取最小值，CPU 11–25%）

- 复测与实现者一致（57 → 65 / 59 → 67）。代价来自展开后的 9 次 vec4 累加本身，加分支、只累加左半都降不下来。
- 门槛口径：DEV_SOP 第 5 节与 README 速查表的原文是「单任务 ≤ 10%（**关键路径程序**的离线 FXC 最小值），一波累计 ≤ 15%」；「增量 > 5%」只是必须派审查的触发条件之一，不是验收门槛。cloud-resolve 在启动的 `compileAsync` 批次里与 cloud-march（约 500 ms）、窗外、舱内并行编译（`compileTargets()`，main.ts 623–654 行），**不是关键路径**，关键路径程序没有变化。**建议接受**，写进编译预算账本即可，由波次收尾的安静窗口统一确认。

## 开发体验反馈

- **哪里慢**：冷编译变体对照约 4 分钟；逐位对照脚本加 7 个场景的平均截图，一轮约 6 分钟；等测量锁大约 1 分钟（shader-budget，pid 15812）。其余是读代码。
- **`freeze()` 每次调用都重设冻结时刻（实现者发现），核实如下**：main.ts 386–388 行 `frozenNow = on ? performance.now() : null`，已经冻结时再调一次，下一帧 `dt = 新 − 旧`（上限 0.1 s），位置、模拟时间、whiteout、uTime 会推进一步。**正式工具不受影响**：`shots --pair`（含 `--base-shader --cloud-live`）每个场景只在 pinGeometry 之后调一次 freeze(true)，a / b / a2 之间不再调；`flicker --cloud-live` 也只调一次。只有自己反复调用 freeze 的脚本（如 `C11-ab.mjs`）才会中招。**建议修 main.ts**：`frozenNow = on ? (frozenNow ?? performance.now()) : null`（已冻结时保留原来的时刻），一行改动，所有脚本都不用再绕。
- **判 resolve / 累积类改动的零回归，不要用「整屏冻结截图相减」**：rAF 插帧和云影图分片会把测量弄脏（见证据第 1 节）。「同一组输入，两个程序各画进一张临时目标再逐位比」这个做法几秒出结果、完全确定，而且能顺带扫 imm、画质档。建议 DX 收进 dev-browser，例如 `exact --material clouds.resolveMat --base-shader <端口> --uniform uCloudImmersion=0,0.02,1`。脚本在 scratchpad 的 `c11rev-exact.mjs`，没有收进仓库；需要的话可以从本报告的描述重写，核心是 `resolveMat` 换源后 `pass.render(m, 临时目标)` 两次。
- **`shots --pair --base-shader --material clouds.resolveMat --cloud-live` 对 resolve 可以用**：b 能正确显示 master 的棋盘纹，a2 也回到了 a。但因为是 cloudLive，a / b / a2 之间云还在演化（中间有 benchFrame(30)），只适合比统计量，不能逐像素相减。README 的调试一节可以补一句。
- **踩到的小坑**：`shots --out` 相对的是**当前 worktree 的仓库根**。在 `tmp/c11rev` 里跑时，截图落在 `tmp/c11rev/tmp/screenshot/...`，删 worktree 前要记得搬出来。文件头写了「相对仓库根」，但没有提醒 worktree 的情况。
- 其余：无。
