## 问题（按严重度）

### 低 1：「云里用 IGN」的阈值 0.5 不是最优，但影响很小

复核时顺带发现：在**部分浸入**（wImm ≈ 0.44–0.54）时，蓝噪声的单帧归一相邻差反而比 IGN 低。in-cloud (−10,−5) 上，0.45 时 0.0918 对 0.1077，0.55 时 0.0717 对 0.0843；(30,−5) 上是 0.0505 对 0.0586，约 ×0.85。完全浸入（ramp 末段 w ≈ 0.95）时才轮到 IGN 更好：0.0171 对 0.0203，帧间变化 0.0275 对 0.0374，与实现者报的 ×1.2 一致。所以两者的交叉点在 0.5 以上。

whiteout 按 τ = 0.5 s 平滑，进出云时从 0.5 走到 0 或 1 只要零点几秒，阈值放在哪里几乎看不出来，**不要求改**。以后如果改 C11 的 3×3 平均或 whiteout 的平滑，要连阈值一起复核，可以考虑挪到 0.7–0.8。建议在 README 坑二补一句「部分浸入时蓝噪声更好，交叉点在 0.5 以上」。

### 低 2：交接报告漏报了运动口径的斜纹指数

`motion\metrics.txt` 里斜纹指数几何均值 ×0.983（最差 ×1.12，noon / sunset 反而升高），交接报告只写了运动时对角高频 ×0.86。原因可能是重投影的双线性取历史沿运动方向产生了相关，指标分不出「沿运动方向的糊」和「斜纹」（另外各变体的机位也不同）。**斜纹指数只能用于静止、同机位的 A/B**，这一点要写进 C12.md 和 README 坑三，以免后来者拿运动数据去否定或证明斜纹。运动时目视（z-motion 图）是可信的。

### 低 3：UNORM 解码有个极小的非均匀

生成器写入的是 `floor((rank+0.5)/N·256)`，也就是 0..255，每个值恰好 64 次；GPU 读回的是 k/255，所以 k = 0 和 k = 255 在 `fract(bn + φf)` 之后落在同一点。结果是 256 个值里有 2/256 的像素共用一个抖动值，相邻值的间距是 1/255 而不是 1/256。对均值没有偏差（均值正好 0.5000），对画面也没有可测的影响。想要干净，在着色器里写 `(bn * 255.0 + 0.5) / 256.0` 就行，零成本，可顺手做，也可不做。

### 无问题（核实过的项）

1. **切换机制**：`blueNoise()` 里 `if (uCloudImmersion > 0.5)` 是**运行时 uniform 分支**，不是 define，两条路径编进所有变体（冷编译增量可忽略，见上）。同一帧内全屏走同一边，没有分支内导数问题（texelFetch 不需要导数）。`uCloudImmersion` 与曝光的 whiteout 是同一个 uniform 对象：`immersed = smoothstep(cameraDensity, 0.01, 0.08)`，探针每 4 帧一个值，再按 τ = 0.5 s 指数平滑，所以是平滑量。步进的各变体材质共用 `marchMat.uniforms`，`uBlueNoise` 和 `uCloudImmersion` 在所有变体里都有值。
2. **纹理**：RG8、`NearestFilter`、`RepeatWrapping`、无 mip、`unpackAlignment = 1`。着色器里用 `texelFetch(…, ivec2(gl_FragCoord.xy) & 127, 0)`，不经过滤，也不依赖 wrap 模式。画质档 0.75 / 0.5 时 `gl_FragCoord` 是云缓冲的像素坐标，蓝噪声按云像素铺，上采样后颗粒大 1.33–2 倍，仍然各向同性，是正确的。
3. **生成确定性**：在复核 worktree 里重新生成，校验和 `db878300`，与提交的文件逐字一致，耗时 1.1 s。算法按 Ulichney 的 void-and-cluster 实现；第二、三阶段合并，在环面上核总和恒定的前提下是等价的（0 的最紧簇 = 1 的最大空洞，自身项也算对了）。σ = 1.5、窗口半径 8，截断误差约 1e−6。
4. **频谱**（`c12rev-bn.py`）：R / G 两个通道在 r < 0.2 的能量都只有 0.03%；r ∈ [0.2, 0.5] 分 8 个方向扇区，能量变异系数 R 0.059、G 0.032（最大 / 最小 1.21 / 1.10），各向同性，属于教科书级的蓝噪声。作为对照，IGN 的扇区变异系数 1.10、最大 / 最小 15.2，这正是斜纹的来源。加 φ 取 fract 以后，低频升到 1.3–1.4%（IGN 1.9%，白噪声 13%），与实现者的 `C12-bnspec.py` 一致。两个通道的相关系数 −0.002，错位 ±1 的互相关都在 |0.011| 以内。
5. **平铺重复**：在 8 场景的实时单帧里（`final\*\f*.png`，16 帧取平均），高通残差在位移 128 / 256 px 处的自相关都在 |0.01| 以内，与 127 / 129 px 的对照和 IGN 没有差别（`c12rev-tile.py`）。原因是残差由「蓝噪声值 × 当地云的梯度」共同决定，云在变，残差就不周期。128² 蓝噪声本身没有低频，平铺时拼缝也看不出来。3200 宽（DPR 2）铺 25 列，性质相同。「屏幕空间固定的颗粒、云在它下面移动」这个纱窗感，IGN 本来就有，不是本任务引入的。
6. **近有理关系**：C03 审查的推理（逐像素 (jitter, gDetailRnd) 的时间联合分布只由增量对 (0.618, √2−1) 决定，空间项只决定图样）与空间项是什么无关，**依然成立**。本任务没动增量，也没动 `+ i·φ` 这一项。两个空间项现在来自两张独立生成的图，比原来「IGN 与转置平移的 IGN」更干净。
7. **sampler**：静态数了全部步进变体（`c12rev-samplers.mjs`，按 lint-shaders 的 samplerAudit）：默认 / 卷云 8/16，奇观 9/16。浏览器里天气变体 S / T 是 9/16（多出 uOcc）。最坏的组合 WCST 是 8 + uOcc + uWonderSurf = 10/16，有余量。resolve 没有变化（3/16）。
8. **冲突与检查**：见结论。

## 对三个指标的看法

- **「斜纹指数」**（3×3 高通残差在 10 个位移上的自相关取最大值）：用在**静止、同机位的 A/B** 上是合理的。我的仿真里 IGN 残差在 (2,0) 是 +0.66，蓝噪声全部 < 0.05，能把「规则方向结构」和「颗粒」分开，这是 FFT 对角高频做不到的：蓝噪声本身就有 52% 的能量落在对角高频区。它的局限有两条。一是真实的云结构也会被算进去，storm-day 0.46、typhoon 0.28 与方案无关，所以只能比同一机位。二是运动时会被重投影造成的方向性模糊污染（低 2）。建议 README 里说明它的适用口径。
- **「归一相邻差回到 C01 之前」**：同意实现者的判断，这个目标在结构上已经做不到（blend 0.04 时 clouds-variety 仍有 .0201）。验收应改看**噪声分量**：HDR 时间 relStd，或「单帧 − 64 帧平均」的空间 rms。这件事协调者要改 ROADMAP / TASKS 里的验收口径。

## C12b（resolve 时间窗自适应）评估：值得开，但公式要改

**收益是实打实的。** 静止时 blend 0.04 能让对角高频下降 46%、时间波动下降 52%，而且这是真正降噪声幅度的唯一手段。

**风险，按严重度排：**

1. **巡航时亚像素运动的累积模糊（最大风险）。** 历史用双线性取样，每帧以小数位移 f 重采样一次，就叠加一次方差约 f(1−f) px² 的模糊。EMA 的平均年龄是 (1−b)/b 帧，稳态下模糊方差约为 (1−b)/b · f(1−f)：
   - b = 0.12：约 7.3 · f(1−f)，f = 0.5 时 σ ≈ 1.35 px；
   - b = 0.04：约 24 · f(1−f)，f = 0.5 时 σ ≈ 2.45 px，f = 0.15 时 σ ≈ 1.75 px（现在是 0.97 px）。

   邻域夹取只在历史越出 3×3 范围时起作用，平缓的云边照样会糊。按铁律「宁可小，不要糊」，这是硬伤。
2. **实现者建议的公式方向不对。** `mix(0.04, 0.12, smoothstep(0.15, 0.6, 位移))` 按位移**大小**决定 blend，可双线性模糊取决于位移的**小数部分**：0.15–0.5 px 的小位移恰好是糊得最厉害的区间，却会被分到低 blend。远云（30–100 km）每帧只移动 0.1–0.3 px，正落在这里。
3. 云本身的演化（风场偏移、形变）在低 blend 下会滞后约 25 帧（0.4 s），夹取可以兜住，但会有轻微「粘滞」。
4. 转弯 / 滚转、刚出云时，历史有效但内容变化大，低 blend 会拖影。

**建议做法：**

- 先把历史取样换成 **Catmull-Rom（5 tap 的双三次近似）**，这是低 blend 的前提，否则怎么调都会糊。
- blend 按**重采样模糊量**自适应，例如 `b = mix(0.04, 0.12, clamp(4·fx(1−fx) + 4·fy(1−fy), 0, 1))`（fx、fy 是重投影坐标的小数部分），再加上「夹取改动量大时回到 0.12」。
- 另一种做法是把 min/max 夹取换成**方差裁剪**（均值 ± γσ）。它能在不降 blend 的前提下压掉一部分噪声，可以作为备选方案一起 A/B。
- 只改云外。云里（wImm > 0）保持 C11 的现状，免得和 3×3 平均互相影响。

**验收（建议）：**

1. 静止（冻结、同机位）：8 场景 HDR relStd 几何均值 ≤ ×0.6，单帧「单帧 − 64 帧平均」的空间 rms ≤ ×0.7。
2. **运动（解冻巡航 ≥ 120 帧，每个变体同一条航迹，要固定时间与云偏移，参照 C11 的 `__c11freeze` 固定 `performance.now`）**：拿每个变体的 16 帧平均图，对比 master，看云边的 10–90% 边宽，或云边带的梯度能量。**边宽增加 ≤ 5%**，否则返工。最好再加一个参照：同一机位用 blend 0.01 冻结累积 256 帧当「真值」，比较各变体相对真值的 rms。
3. 转弯（滚转 25°、偏航速度 3°/s）和出云后 2 s：拖影 / 残影目视，并量「与真值差」的峰值不超过 master 的 1.2 倍。
4. 1–4 Hz 呼吸：relLow16 在静止和运动两个口径下都不升高。
5. 冷编译：resolve 是小程序，不是瓶颈，但 5-tap 会增加 resolve 的逐像素成本，要用批渲测一次帧时间。

## 开发体验反馈

- **顺利的地方**：实现者的交接非常完整，变体 A/B 脚本 `C12-ab.mjs` 可以直接改来做切换实验（手动推进 `clouds.render` 加上直接写 `resolveMat.uniforms.uCloudImmersion`，整套约 5 分钟）；`shader-budget --only cloud-march` 20 秒出结果，很快。
- **摩擦 1**：`check:glsl` 的 sampler 表只覆盖场景 / 窗外程序，**云步进变体没有 sampler 断言**。实现者要在浏览器里用 `getActiveUniform` 数，我是改一份 lint-shaders 的副本、导出 `samplerAudit` 才数出来的。而且 samplerAudit 只认源码开头的 `#define`，天气变体的 uOcc 在静态审计里漏数（显示 8，实际 9）。建议（DX）：把全部 `cloud-march-*` 变体（含 WCST 组合）加进 sampler 表，并修正宏识别。
- **摩擦 2**：`collectPrograms` 默认好像不列 `cloud-march-CS / WCST` 这些组合（check:glsl 的语法检查里有，我按 id 前缀过滤却没拿到），原因没有细查，建议 DX 核对枚举口径是否一致。
- **摩擦 3**：删除 worktree 时 `git worktree remove --force` 在 Windows 上报 Directory not empty，要用 PowerShell 的 Remove-Item 补删（SOP 已写，照做即可）。
- 耗时：读材料约 10 分钟，离线复核（生成、频谱、平铺）约 5 分钟，浏览器切换实验约 6 分钟，冷编译 20 秒；没有等锁。
