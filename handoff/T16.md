   - 在最前面 `new BootProgress()`；在原有 `tick(...)` 调用旁各配一句 `boot.finish(id)`。
   - **关键发现并修复**：原来只有场景 + 机翼两个大程序走 `renderer.compileAsync` 后台编译，云光线步进（`Clouds.marchMat`）、
     海面 FFT（`OceanWaves` 的三个 pass）、曝光 + 眩光（`Exposure` / `Bloom` 的几个 pass）都是在**真正首帧渲染时第一次用到才编译**，
     会在主线程同步阻塞（比场景/机翼小得多，但确实存在，且原来完全不计时、不出现在进度条里）。
     修法：在场景/机翼后台编译完成之后、真正首帧之前，各自显式调用一次公开方法（`clouds.render()` / `ocean.update()` / `bloom.render()+exposure.render()`）
     强制触发编译并单独计时；调用完立刻调 `clouds.snap()` / `exposure.snap()` 撤销这次「假调用」在时间累积历史、曝光适应历史上留下的痕迹
     （两个 snap 方法本来就是为「跳变后清空历史」设计的，正好复用，不用碰 `clouds.ts` / `render/exposure.ts` 这些不归本任务管的文件）。
     详细的安全性分析（为什么不会污染真首帧画面）见下面「踩到的坑」。
   - `window.__voyageStartup` 语义不变：仍然是首帧渲染完、`renderer.getContext().finish()` 之后才赋值，
     只是内部多了 `云光线步进程序编译` `海面 FFT 程序编译` `曝光与眩光程序编译` 三个新 key，`首帧（含着色器编译）` 改名叫 `首帧渲染`
     （现在大部分编译已经挪到前面几个阶段，这个 tick 更准确地反映真正首帧的开销）。回归脚本只判断 `window.__voyageStartup` 是否存在，不依赖具体 key。
   - `window.__voyage` 调试句柄新增 `boot` 字段（`window.__voyage.boot.debugInfo` 能看各阶段估算/实测耗时）。
