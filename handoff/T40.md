## 背景

用户原话：「有时候窗外能看到其他航空器航行的轨迹，由于预算问题其实是一个拖着轨迹的圆球飞过，露馅了，确保这类内容不要产生航线交错。」

旧版 `spawn()`：交叉角 ±0.6 rad（约 ±34°）随机，横向距离下限只有 8 km。飞机近了角尺寸变大，一个没有机翼、没有机身细节的简化球（`traffic.glsl.ts` 的 `trafficRadiance`）就藏不住了；交叉角还经常让它斜穿我们的航迹，两架飞机的航迹也可能互相交叉。

## 改法

### 1. 最小距离推算（写在 `traffic.ts` 文件头，这里摘要）

1600×1200、默认视场（`render/scene.ts` 的 `uTanHalfFov = tan(25°)`，垂直半视场 25°）下：

```
pixelAngle = 2·tan(25°) / 1200 ≈ 7.77e-4 rad/px
机体半径 size = 0.02 km / dist(km)（traffic.glsl.ts 原有公式，对应约 40 m 机长）
角直径(px) = (0.04/dist) / pixelAngle ≈ 51.5 / dist(km)
```

要求角直径 ≤ 约 3 px（用户给的 2–3 px 区间上限）⟹ `dist ≥ 51.5/3 ≈ 17.2 km`。
取 **`MIN_DIST_KM = 18`**（对应约 2.86 px，留一点余量）。

### 2. 航线设计（`traffic.ts`）

- 对飞（航向与我们相反）允许 **≤3°** 的交叉角（`MAX_CROSS_ANGLE`）；同向慢慢超越（新加的场景，原来只有对飞）**交叉角强制为 0**——这类相遇相对速度小，经过时间长，哪怕一点点交叉角，侧向漂移也会失控地累积，直接不给最安全。
- 出生时的横向距离不是随便选的：对飞交叉角最多让飞机在出生距离（`AHEAD_RANGE` 上限 65 km）内积累 `65·sin(3°) ≈ 3.4 km` 的最坏侧向漂移，所以横向距离下限 = `MIN_DIST_KM + 3.4 + 0.5`（浮点余量）。这个下限保证**全程**（包括它拖出的航迹云——航迹云就在同一条直线上，任何一点到原点的距离都不会比垂足距离更近）离我们 ≥ `MIN_DIST_KM`。
- 两条「车道」`LANES[0]`（约 [21.9, 33.9] km）/ `LANES[1]`（约 [48.7, 61.3] km）留了 ≥ 2×最坏漂移 + 8 km 的间隙，两条车道的可能范围全程不重叠。`spawn()` 里两架飞机不会分到同一条车道（另一架在飞就取补集车道）。车道 1 的上限还按「出生时仍要留在 90 km 可见半径内」反推过，避免白白浪费生成。
- `spawnNear()`（调试用）遵守同样的 `MIN_DIST_KM` 公式；默认贴着「这个出生距离下允许的最小横向距离」放置，方便截图验证最近点时刻；显式传 `sideKm` 可以刻意压近做压力测试（见下面截图 3）。

### 3. 着色器兜底（`traffic.glsl.ts`）

即使航线设计本身已经保证了最小距离，仍加两层与具体路径无关的兜底：

1. **机体显示半径按像素数夹住**：`dispSize = min(size, BODY_MAX_PX * pixelAngle)`（`BODY_MAX_PX = 1.4`，半径，对应约 2.8 px 直径）。哪怕算出来的真实距离意外偏近，画出来的也只是一个小亮点（航行灯 / 太阳一闪的量级），不会随距离继续变大成一颗明显的假球。
2. **航迹云按「离我们最近的一点」整体安全淡出**：对每架飞机的尾迹线段，额外算一次「离原点（我们）最近的点」（不是原有的「离视线最近的点」），距离低于 `TRAFFIC_MIN_DIST_KM`（=18，需要和 `traffic.ts` 的 `MIN_DIST_KM` 保持一致，两边各有注释互相指向）时整条尾迹淡出，避免任何路径下画出一条贴着摄像机、穿过前方视野的粗亮线。

## 坑（已写进 README 坑点，这里摘要）

**远处交通工具（飞机）的简化球模型，近距离会露出「其实是个球」的破绽**：机体没有机翼 / 机身细节，只是按角尺寸画的一个均匀亮斑，角直径超过几个像素就会被识别为「一个放大的圆点」而不是飞机。两层修法：①航线设计上保证全程与我们的最小距离（按目标屏幕像素数反推，见上面的推算公式），且两机不共用车道、车道间留够间隙防止互相交叉；②着色器兜底：机体显示半径按像素数夹住（超过阈值只留一个不再变大的小亮点）、航迹云按「离我们最近的一点」整体淡出。以后再加别的「预算内简化模型」（例如更远处的船、车）时，可以复用同一套思路：先算「肉眼看出简化痕迹」对应的像素阈值反推距离，再让生成逻辑保证这个距离，最后在着色器里按像素尺寸夹住做兜底。

## 还不够好 / 下一轮

1. 车道目前是硬编码的两条固定区间（不随视场角自适应）——如果以后 FOV、分辨率假设变了（比如换到更宽的画布），`MIN_DIST_KM` 和 `LANES` 需要跟着改（公式都在文件头，改起来不难，但不是自动的）。
2. 双机同时出现时，车道 1（较远那条）的飞机在明亮天空背景下有点不容易注意到（角直径约 1 px 量级，далеко、低对比度），这是刻意的（更远就应该更不显眼），但截图 4 需要额外给两架飞机一点点沿航向的偏移才能让它们不重叠在同一块屏幕像素上——真实游戏里两架飞机沿航向的分布本来就是连续随机的，不会真的重叠。
3. 没有做「本来就很拥挤的空域会不会导致两个respawn 计时器长期错拍导致 lane 分配退化」之类的长跑测试；离线脚本只测了两架同时生成的最坏情况（真实游戏里错峰生成时车道间隙只会更大，更安全）。

## 开发体验反馈

- **哪里慢**：`pnpm install`（这个 worktree 首次用，node_modules 缺失）和 dev server 冷启动加起来约十几秒，不算慢；主要时间花在设计航线的「最小距离 / 两机不交叉」数学推导上（想清楚「车道」怎么分、交叉角往哪个方向转是安全的），代码本身不大。
- **哪里卡**：调试双机截图时，一开始给的 `aheadKm` 偏移（±10~15 km）太大，第二架飞机就飞出了舷窗那个椭圆形可视孔径之外（相机名义 FOV 比实际能透过舷窗看到的角度宽得多），排查了一会儿才意识到是取景问题，不是 uniform 同步的问题——写了个小的诊断脚本（`page.evaluate` 读 `sceneMat.uniforms` 里的 `uTrafficPos/Dir/Active`）确认数据是对的，再缩小偏移量就看到了。
- **怎么绕过去的 / 希望有什么**：如果以后还有类似「舷窗可视角比相机 FOV 窄很多」的调试需求，一个「给定世界坐标点，返回它是否落在舷窗可视孔径内」的小工具函数（哪怕只是调试用、临时加在 `window.__voyage` 上）会省不少试错时间；这次是靠手动缩小偏移量试出来的。
