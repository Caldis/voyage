# W00 · 云步进里的「奇观层」（交接 / 接口说明，给 W02、W03）

分支 `worktree-agent-ac2380f3f3befc81f`，端口 5200，对照 5290（scratchpad 里 master 的解包副本）。截图 `tmp/screenshot/W00/`。
设计依据 `research/WONDERS.md` §3.3 方案 A。状态：**已交付**。

## 一句话

云间层奇观 = 「奇观 pass 把表面 + 介质合成一层（辐亮度、不透明度、深度）」+「云步进的奇观变体走到那一深度时把这一层插进去」。
前面的云挡它、它挡后面的云，一起进时间累积（重投影用合成后的深度）。没有云间层奇观时画的是原来的步进程序（预处理后逐字相同）：**零开销、冷编译不变**。

## 管线（`src/clouds/clouds.ts`）

| 程序 | 什么时候画 | 做什么 |
| --- | --- | --- |
| `marchMat`（默认） | 平时 | 原样。奇观代码全在 `#ifdef WONDER_LAYER` 里 |
| `wonderSurfMat`（`WONDER_SURF_FRAG`，奇观 pass） | 有云间层奇观在场（`uWonderVol > 0`）且已编好 | 云分辨率，只算窗板内、视线穿过包围盒的像素：球面追踪表面 → 在表面之前步进介质 → 合成一层。输出 RGBA32F：rgb 预乘辐亮度（不含空气透视），a = floor(tW·8) + 不透明度·0.998 |
| `marchWonderMat`（`#define WONDER_LAYER`） | 同上 | 读同一像素的 texel；步进走到 tW 时 `L += T·Lw; T *= 1 − αw`；αw ≈ 1 时身后的云不走；受光时对投影椭球求影子（每条视线预先算好影子柱区间，循环里只做区间判断）；没有云的视线也输出这一层 |

- 两个奇观程序第一次需要时在后台编译（`compileAsync`，检查 `diagnostics.runnable`），d3d11 冷约 13–17 s；编好之前奇观不画、云照常。`clouds.wonderLayerState`：idle / compiling / ready / failed。`clouds.wonderPrewarm = true` 可以提前编。
- 空气透视沿用云的做法：按整条视线的加权深度统一加（奇观只挡在云的一侧时深度就是奇观自己的深度）。

## 注册一个云间层奇观（W02 / W03 照做）

1. **GLSL**（`src/wonders/wonder-cloud.glsl.ts` 的 `WONDER_CLOUD_KINDS` 加一项；建议把源码放新文件，如 `wonders/city.glsl.ts`，这里只 import）：
   ```ts
   { id: 2, name: "雾海灯城", glsl: CITY_GLSL, sdf: "citySdf", shade: "cityShade", medium: "cityMedium" }
   ```
   - `float sdf(vec3 q)`：到表面的距离（km），**必须是真实距离的下界**；可写 `gWonderMat` 区分材质（命中时的值传给 shade）。
   - `vec3 shade(vec3 q, vec3 n, vec3 pW, vec3 nW, vec3 rd)`：表面辐亮度（kcd/m²，不含空气透视）。q / n 局部坐标，pW / nW 窗外坐标（相机在 (0, uCamR, 0)）。标准受光用 `wonderLitSurface(pW, nW, albedo)`（主光源 × 云影图 + 天光 + 下方云海反光）；自发光（灯格、火光）直接加。
   - `float medium(vec3 q, out vec3 albedo, out vec3 emit)`：返回消光系数 σ（1/km）；albedo 单次散射反照率；emit 体积自发光（kcd/m² / km，σ = 0 也行，例如光束、辉光）。受光由 `wonderMediumLight` 统一算：主光源 × 云影图 × 投影椭球 × 多次散射相函数（和云同一套近似）+ 天光。**「灯火从下往上照雾」这类光请自己算进 emit**（例如 emit = σ·反照率·灯火场照度 / 4π）。
   - 可以读 `uWonderParams`：x = reveal（0..1），y = 时间（真实秒，1 小时循环），zw = catalog 里的 `volume.params`。可以用 CLOUD_COMMON 的噪声（`uShapeNoise` 等）。
   - 函数一律带模块前缀；三个分派函数各只有一个调用点。循环上界写成「常数 + `min(uStormCount, 0)`」防 FXC 展开。
2. **catalog**（`src/wonders/catalog.ts`）：`layer: "cloud"`，写 `volume`：
   ```ts
   volume: { kind: 2, baseKm: 0, box: [[-40, 0, -40], [40, 4.5, 40]], surface: true, medium: true, stepKm: 0.3,
             caster: { center: [0, 2, 0], radii: [3, 2, 3] }, params: [0, 0] }
   ```
   - **局部坐标**：原点在锚点（地面经纬度）正下方海平面再抬高 baseKm；x 东、y 天顶、z 南。WonderSystem 在 CPU 上用双精度算好「相机 − 锚点」，着色器里没有 6000 km 大数相减。
   - **box 越紧越省**：奇观 pass 只算视线穿过盒子的像素；表面、介质都必须在盒内（盒外的不画）。
   - `stepKm`：介质步长；盒内另外保证 8–96 步（上限 96）。
   - `caster`：可选；挡住云（和奇观自己的介质）受到的直射光。
3. 奇观种类没编进奇观 pass（`wonderVolumeCompiled` 为假）时不会进候选。

## 限制（接口层面的，已知、有意为之）

- **一条视线上奇观只算「一层」**。包围盒里与奇观交错的云，顺序按那一层的加权深度近似：在它之前的云挡整层、之后的被整层挡住。岛 / 城与云分得开时正确；雾罩里穿插的碎云会有偏差。要更精确就得把介质写回云步进本身，但那会让变体慢一倍（见 README 坑点）。
- 介质没有沿光线步进自己（雾罩自己的影子只靠投影椭球近似）；云影图只算 3 km 以上起点（`cloudShadow` 的限制），奇观高于所有云时不查。
- 表面命中的像素覆盖率一律按 1 算（只在没命中的一侧做半像素渐变）：近水平的轮廓有 1 像素级的台阶，时间累积不抖动像素中心，所以不会被抹平。W03 若嫌台阶明显，可在奇观 pass 里给像素中心加亚像素抖动（只影响奇观 pass）。
- 奇观 pass 与云同分辨率，画质降档时跟着变低；细线类（天梯）不要走这条路。

### 走过的弯路（为什么是现在这个结构）

1. 第一版把表面追踪、介质、投影都直接写进 `MARCH_FRAG`（uniform 分支，奇观关时一次都不走）：noon-cumulus 云步进 0.35 → 0.73 ms，台风 ×2。逐段删除归因：单删哪段都不够，程序会在 0.35 / 0.72 两档间跳。
2. 改成 `#ifdef` 变体 + 表面单独 pass：默认程序回到 0.35；但变体里还有介质的逐步采样，奇观在场时仍 0.74–0.8。
3. 介质也挪进奇观 pass、只合成一层：变体只剩「读 texel + 插入 + 投影区间判断」，0.47。

## W01 天梯 / 建木要不要迁到新接口：**不迁**

- 天梯 / 建木是 330–410 km 外、亚像素宽的细线，现在在窗外程序里全分辨率解析绘制、按像素覆盖守恒；迁进奇观 pass 就变成云分辨率（降档时 0.5×），还要吃时间累积，细线会糊、会闪——违反「宁可小，不要糊」。研究文档 §3.3 也写明细线类不走这条路。
- 遮挡：它画在背景上、云合成之前，**比它近的云**都正确挡住它（W01 的 tether-cloud 截图）。唯一的偏差是**比它远的云**也会画在它前面：只可能发生在它底部接近地平线的一小段（基座在 330–410 km 外，身后的云在 400 km 以内、贴着地平线），那一段本来就按距离和高度渐隐进霾里，看不出来。
- 它不需要遮挡身后的云（身后的云在它下半截的地平线霾里）。所以现在的「天幕层」做法已经是对的，迁移只会更差、更贵。

## 协调者追加：手动召唤朝向 + 「建木召唤后看不见」

**改法**（`system.ts`）：面板「立即召唤」（`trigger(id, { riseS, forwardOffsetDeg })`，没给方位、没给距离、via = summon）改成放在**相机此刻视线的水平方位**上，±10° 以内三角分布随机偏移，距离取该奇观的正常范围。面板传的 forwardOffsetDeg 在这里不用；自动出场、借遮挡、调试脚本（给了方位或距离）照旧。需要 main.ts 接 `wonders.attachView(sceneMat.uniforms)`（上面的片段）；没接时退回原来的「窗口正对 + 偏机头」。
验证（`handoff/W00-summon.mjs --attach`，默认坐姿、正午晴空）：视线方位 269.8°，天梯落在 270°、建木 267°（改前两个都在 265°）。

**建木「什么都没看到」的根因**：**不是刷在视野外**——改前它也在 265°，在窗板以内（视线 269.8°）。是**白天亮度对比太低**：正午时它和天梯的线与背景天空的差 **< 1/255**（截图逐列测：0.1–0.3 / 255），只有把对比拉到 6 倍才看得见（`tmp/screenshot/W00/summon/summon-*-stretch6x.png`）。原因是 W01 的取值：缆索 / 树干反照率 3.5% / 5%，390 km 外视线上的天空亮度几乎全来自它前面的空气（空气透视内散射），暗色细线挡掉的那一点背景光在 8 位里舍掉了；建木没有航标灯，白天就彻底没有可见的东西。黄昏（上段被阳光照亮）才是它们的出场时段。另外默认机翼位置下窗口正中是翼尖小翼，线正好落在小翼旁边，更难找。
按简报**没改建木造型 / 亮度**；要解决白天可见性，需要单独定：提高白天反照率（W01 交接写过「0.06 以上黄昏晕成光柱」的取舍）、或白天召唤时给一个亮的特征（例如建木的暖金段）。
