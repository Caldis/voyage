## 结论：返工（小，一项）——去掉形状噪声 mip 封顶，其余通过

1. **效果成立**。用户截图那种「平面轮廓往上挤出的豆腐块 + 竖条纹」，在 v-cu-6000、vs-tow-a8、noon-cumulus 的远排，以及低空擦云层（cu-3800-graze）放大 ×3 后都看得出**确实没了**：平顶长条面包变成高低错落的圆顶团，竖肋基本消失。clouds-variety 云海顶面起伏更大、空隙更多，是改进。层积云、雷暴、台风近似不变。
2. **性能超预审上限，而且比交接自报的还多**。复测 3 轮，云 pass：noon ×1.12–1.16，variety ×1.17–1.19，cu-6000 ×1.14–1.17，cu-side ×1.19–1.23。上限是 +5%（掠射 +8%）。增量分两块：
   - **mip 封顶**（纹理带宽）：约 5–10 个百分点。收益小（远排竖肋靠竖直频率就已经大半去掉了），代价是远处时间噪声。
   - **云变高、有云样本变多**（「正确代价」）：noon +5–7%、cu-6000 +9–10%、variety +15%、cu-side +15–19%。步数几乎不变，所以这部分只能接受或另找抵消。
3. **推荐：去掉 mip 封顶，也就是交接里说的 `SHAPE_LOD_MAX=6`**。建议直接删掉这个常量，恢复原来的 `lod` / `max(lod - 1.0, 0.0)`：
   - 省下 noon 约 7–10 个点、cu-6000 约 5–7 个点；
   - 远处时间噪声从 ×1.26 / ×1.39 降到 ×1.20 / ×1.26（cu-6000 远排 / tow-a8）；
   - 远排放大看，和封顶版几乎没差别（`z/cu-6000-far3a/b.png`、`z/noon-horizon-lod6.png`、`z/tow-far-lod6.png`，只在 tow-a8 约 200 km 的地平线带左段有很淡的竖纹）。
   - 按铁律「锯齿 / 闪烁最高优先」，这笔账也该这么选。
4. **剩下的「变高代价」，建议接受并入账**，改完以后 noon 约 +5–7%，variety / cu-side 约 +15%。
   - 这个代价换来的是用户点名的缺陷；有云样本变多是体积本身变了，不压体积省不下来。我试了「积云族 d 随高度线性收 0.2 / 0.35」（taper），反而**更贵**（variety ×1.27、cu-side ×1.38：云变薄，视线走得更远），又把云压扁，已否决。
   - **等 PERF-STORM 抵消不成立**：PERF-STORM（671929d）只改天气程序（`#ifdef CLOUD_WEATHER` 的空域跳跃），noon / variety / cu-6000 走的是默认程序，一分钱也抵不到。
   - 要协调者 / 性能总监做的：把 variety 在用户分辨率下约 +0.38 ms（2.54 ms × 15%，总量约 6.0 ms，占 96%）记进预算账本。**本波晴天碎积云的云类余量已经被 C-TOFU 吃完**，C06 在 variety 上的预算要重新分配，或者另排一个默认程序受光步进的 PERF 任务来抵消。
5. **不需要再派审查**。返工只删一个常量、改两处 textureLod，协调者核验 `gpu-ab`（noon ≤ ×1.08、cu-6000 ≤ ×1.12）和 `ab` 远排截图即可合并。README 坑点和交接里「mip 封顶 3」那句跟着改，写上「封顶试过：+5–10% GPU、远处噪声 ×1.05，收益小，已撤」。

### P2【美术 · 新形状】中距离少量「悬挑 / 拱形细臂 / 细柄蘑菇」（不阻塞，交 TW03）

- 证据：`z/cu-6000-hook.png`、`z/cu6000-mid-b.png`（6 km 机位，约 20–50 km）。个别云有一条横伸出去的细臂、拱形，或者圆顶坐在比它窄的柄上。
- 成因（读代码推断）：竖直频率提高后，同一列的噪声强度随高度变。`cumulusTop()` 的 σ 取的是**本样本**的 d，不是「这一列」的强度，所以腰部比底部强的地方就长成外挑。
- 出现频率：一屏一两处，远低于原来整排的豆腐块，所以不阻塞。
- 之前以为云下方的「飞碟」暗椭圆也是这个问题，放大后确认那是**云落在海面上的影子**（旧版同样有），不算。
- 修法方向（给 TW03）：σ 改用竖直方向一致的量，例如 `nB` 在层中高度处多取一次，或用天气图强度。这会多一次取样，要过预审。这次试的「按高度线性收」（taper）能减少外挑，但更贵、云更扁，不推荐。

### P2【美术 · 近处】cu-side 近处的塔软成一团雾（C06 问题被暴露，不算 C-TOFU 的回归）

- 证据：`z/cu-side.png`。相机在浓积云层（1.4–6.5 km）里 4.5 km 处，强的塔现在能长到 5–5.5 km，贴到相机跟前，读成失焦的白团，天边还有几个光滑的白球。

### P3【连续性】uCuShape 随层厚连续变，形状会「滑」，1× 时看不出

- `cumulusShape()` 每帧在 CPU 上按层厚 / 云型算。导演的连续项按限速推进（云顶 3 km/h、云型满幅 30 min，推送间隔 ≥ 0.25 s）。
- 层厚每推一次（≥ 10 m）引起的竖直倍率变化，相当于 3 km 高处的噪声图样竖直滑约 13 m，1× 时约 1 m/s，比风飘小一个量级，看不出。
- 换云族走的是「淡出到 0 再切 / 借遮挡硬切」，所以权重 w 的 0 ↔ 1 跳变发生时窗外没有可见的积云；换预设走 `snap()`。**不跳**。
- 雷暴程序和默认程序共用 `layerDensity` 与同一个 uniform 对象（`...this.uniforms` 共享引用，`marchVariant` 用的是 `marchMat.uniforms`），所以雷暴出现 / 消失时积云层**不会跳**。storm-cu 截图也确认雷暴本身不变。
- 可选改进（不要求）：噪声竖直坐标用 `(alt − uCloudBottom)·va` 而不是 `alt·va`，层厚变化时图样绕云底伸缩、不整体平移。这会改变外观，要重拍。

## 开发体验反馈

1. **`ab` 的 `time` 参数是分钟**（720 = 12:00）。我按「时分」写成 1500 / 1600，拍成了半夜，白跑一轮。建议 `scenarios` 接受 `"15:00"` 字符串，或者数值 ≥ 1440 时直接报错。
2. **flight 的 `--jobs` 相对路径按 worktree 根解析**。在 `apps/voyage` 下照交接的 `handoff/C-TOFU-flight-jobs.json` 写会找不到文件。交接的「复现」一节应写成 `apps/voyage/handoff/...` 或绝对路径（交接的复现命令需要更正）。
3. **gpu-ab 在排队拥挤时结果会整轮失真**（第 2 轮 IQR 24–78%），工具只把它标成「在离散度内」，没有作废。建议 IQR 超过 15% 时直接判「不可信，请重跑」。
4. **「等某个 PERF 任务抵消」要先核对程序**：抵消项和被抵消的代价要落在同一个着色器变体里。建议预审模板加一栏「此增量落在哪个程序（默认 / 天气 / 卷云）」。
5. `C-TOFU-stack.py` 这类竖排放大拼图脚本很好用，建议收进 `scripts/`，作为云类审查的通用工具。
