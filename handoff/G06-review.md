## 1. 夜间道路爬行 +21%：不是新走样

复现（飞机沿航向前进 4 m/帧，不是只平移头部；`G06_MOVE=4 … night-city --debug 24`）：

| 版本 | 爬行（二阶差分 / 亮度） | 块能量 CV p90 / p98 | 空间锐度（相邻差 / 亮度，自算） |
| --- | --- | --- | --- |
| master | 0.0762 | 0.082 / 0.123 | 0.104 |
| G06 | 0.0930 | 0.070 / 0.110 | 0.120 |
| E2：矢量缩放级改按 RES 选（和 master 同一距离的路网完全一致） | 0.0927 | 0.069 / 0.114 | 0.119 |
| E3：**只把 GROUND_RES 改回 1024**（mip + 各向异性 + textureGrad + 直传全保留） | **0.0762** | 0.084 / 0.125 | — |
| E4：道路选级下限钳在 7.8 m 纹素（和 master 的近处钳位一致） | 0.0929 | 0.070 / 0.110 | — |
| E5：夜光按 2048 取、不做 Worker 放大 | 0.0923 | 0.070 / 0.110 | — |
| E7：影像一律按 1024 取缩放级 | 0.0888 | 0.077 / 0.104 | — |

（E* 都是在临时 worktree 里临时改一行、测完即还原，分支代码没有动。实现者自己做的 `lodR + 1` 实验 0.0935，和 E4 一致。）

判断：
- **E3 是关键**：mip / 各向异性 / textureGrad / 直传全在的情况下，只要纹理回到 1024²，爬行就和 master 完全一样。所以采样方式没有引入时间走样。道路读 A 用的都是 `textureLod(…, 0.0)`，没有按 mip 平均过的距离场参与，下面 §4 逐条核对过。
- 选级（E4）、矢量缩放级（E2）、夜光（E5）都不是原因。增量跟着 2048² 栅格出来的路网内容走：线更细、更干净，道路总亮度 −9%，亮像素数基本不变。空间锐度 +15%，爬行 +22%，两者同步上升；块能量（整片闪不闪）反而更好。按行带看，增量在中段和近处（远→近：0.059/0.093/0.071/0.059/0.073/0.096 → 0.057/0.097/0.084/0.079/0.097/0.113）。
- 目视（`zoom2.png`、`seq.png`，同一机位放大、连拍 f04–f08）：master 的线粗，边缘毛糙，沿线有很多 1–2 像素的竖向「毛刺」；G06 的线细、平滑，毛刺少一些。两边都还剩同一种毛刺：横向道路上方的短竖刺，也就是沿视线方向的像素阶梯。这是 T43 以来就有的残留（`groundRoadCoverage` 沿长轴最多 6 个取样，加上 `real` 梯度门限挡不干净的假线），不是 G06 新增的。线变细以后，它在「÷ 亮度」的指标里占比更大，所以读数上升了。
- 为什么恰好在 2048² 时线变细，我没有追到最后一步：E2 / E4 / E5 排除之后，按米计的纹素、路宽编码都相同，剩下的差别在影像（E7 影响约 1/3）和栅格化的对齐方式上。这不影响结论，但如实记下。

**不要求为此返工。** 建议另开一个小任务（放在 G05 或 T43 续）专门治这种「沿视线方向的短竖刺」。修法方向（按优先级）：
1. 长轴取样数 `n` 的上限从 6 放宽，或者按 `longM / tex0` 取样时加一个与帧无关的旋转抖动（世界坐标哈希，不是时间抖动），让阶梯不再成列；
2. 帐篷核半宽 F 在长轴方向用 `spacing` 的 1.0–1.5 倍，而不是正好等于间距（目前相邻子足迹之间没有重叠，线恰好压在两个取样点之间时能量会跳）；
3. 道路层单独加 lod bias 0.5（只作用于 `lodR`，影像不动），用一点锐度换稳定。实现者的 `+1` 实验说明整级偏粗没用，所以只能作为最后的手段。

## 2. 代价与「2048² 只在高档」的折中

核对实现者的数字，并补充判断（这一项我没有重跑流量 / 加载计时，按 SOP 只在必要时测）：

- **首载 13.4 → 33.7 s**：`update()` 从最粗一级往细建，着色器按 `valid` 退到粗一级，所以画面先出粗级再逐级变清楚。这个行为以前就有，只是时间长了约 2.5 倍，期间会看到 3–4 次「一圈变清楚」的跳变。这是「低清贴图露出来」时间变长了，不是新问题，但违反「宁可有雾」的时长翻倍了。建议：**首载时各级先按 `fine = false`（1024 的缩放级，瓦片数 1/4，≈ master 的 13 s）出一版，全部就位后再在后台升级成 fine**。升级只是锐度的微增（同一片影像细一级），不是方块 → 清晰的跳变。代码里已经有「非 fine 的级别在流速降回来后重建」的路径，初始化时把 `rate` 当成 > 2 处理、`pending === 0` 后放开就行，改动很小。
- **显存 60 → ~315 MB**（两张 7 层 2048² RGBA8 带 mip）：5090 无所谓；集显 / 4 GB 独显上会和云体积纹理、HDR 目标一起挤。另外 G03 高清合成在 2048² 时 Worker 里临时要约 240 MB 浮点缓冲（用完释放）。
- **EOX 1× 85 → 158 次 / 分**：`HOST_LIMITS` 给 EOX 的是 1200 / 分、突发 400，合规。60× 下按 1024 取、和 master 持平（657–737 vs 716–726）。那一次 116 条 CORS 错误大概率是当天测试总量累积造成的，建议波次收尾时在安静时段复测一次。
- **1× 巡航 7–11 帧 > 16.7 ms，主线程空闲，在 GPU 侧**：我认为主要来源是 `uploadDirect` 里的 `gl.generateMipmap(TEXTURE_2D_ARRAY)`。它对**整个数组 7 层、每层 12 级**全部重算，每传一层就把 2 × 7 × 16 MB 的 mip 链重做一遍，其中 6 层白做。5090 上是几毫秒，集显上会成倍放大。three 的回退路径一样，也是整组生成。**跟进修法**：Worker 里在拼好这一层之后顺手做 2× 盒滤波 mip 链（RGB 在线性空间平均；A 通道按语义单独处理：影像 A 只保留「有影像比例」、编码宽度不下传，水体 A 直接给 1.0），主线程按层、按级 `texSubImage3D`，不再调 `generateMipmap`。这样同时把 §4 提到的「mip 里 A 的偏差」也消掉了。上传量多 1/3，但分块直传已经证明 4 MB 一块很便宜。
- **画质档折中**：同意「高」用 2048²、其余用 1024²。但 `GROUND_RES` 同时是纹理的不可变尺寸（texStorage3D）、着色器常量（选级 / 纹素换算 / 道路 / 火车远景都用），换一次要重新分配 2 × 150 MB、重编窗外程序、重下全部瓦片。所以**不能让 PERF-5 自动档在运行时来回切**：大雨时降档、雨停后升档，会触发整套重建和几十秒模糊。建议：
  - 启动时定一次：自动档按 GPU（`WEBGL_debug_renderer_info` 的集显关键字，或 `MAX_TEXTURE_SIZE` / 首帧基准）选 2048 或 1024；面板里手动选「中 / 低」时，提示「地面精度下次载入生效」；
  - 着色器里把 `GROUND_RES` 换成 uniform（或者按两种取值编两个变体）。它只参与标量换算，换成 uniform 对冷编译基本没影响；
  - 1024 那档把 `anisotropy` 也保留：E3 显示 1024² + mip + 各向异性的爬行 / 块能量与 master 相同，白天近地平线的闪烁还更低，低档也值得用。

## 3. 直接调 GL 上传（`attachGl` / `uploadDirect`）

逐条核对了 three r186 `WebGLTextures.uploadTexture`：
- **纹理对象从哪来**：第一次渲染时 three 走 `texStorage3D`（`dataReady = false` 只分配、不传），随后按 `textureNeedsGenerateMipmaps` 调 `generateMipmap`，最后调 `onUpdate`。这时 `state.bindTexture(…, TEXTURE0 + slot)` 已经把激活单元切到这个 slot，所以 `getParameter(TEXTURE_BINDING_2D_ARRAY)` 拿到的就是这张纹理，取法成立。第一次渲染之前到来的上传会退到 `LayerStage` 按层交给 three，也成立。
- **状态缓存**：three 缓存了每个单元的绑定和 `pixelStorei`。`uploadDirect` 只在当前激活单元上绑定再恢复，UNPACK 的 4 个参数读出后原样恢复，GL 的实际状态和 three 缓存的一致。`UNPACK_COLORSPACE_CONVERSION` 对 TypedArray 不起作用，不用管。`texSubImage3D` 的 `srcOffset` 按元素计，写法正确。
- **`needsUpdate`**：直传路径在设置 `needsUpdate` 之前就返回，three 不会再传一遍，正确。
- **resize / 画质切换**：纹理尺寸与画布无关，不受影响。
- **上下文丢失**：`isContextLost()` 时跳过。恢复后 `glTex` 里还是旧上下文的句柄，three 整块重传时拿到空数组，纹理内容丢失、GL 报 INVALID_OPERATION，但不会崩。项目本来就不处理上下文恢复，README 已写明，可以接受。如果以后要做恢复，记得在 `webglcontextrestored` 时清掉 `glTex`。
- **不接这一行时的回退**：`LayerStage.subarray` 按层返回待传像素，three 按层上传，功能正确，代价是每次重建有一帧 10–15 ms（实现者实测）。
- 越界的一行（`main.ts`）和 `light-pollution.ts` 都是必要的最小改动，同意。

## 4. A 通道契约（mip 以后）

| 读取点 | 读法 | 结论 |
| --- | --- | --- |
| `groundRoadTap`：水体 A 的有向距离、影像 A 的照亮宽度 | `textureLod(…, 0.0)` | ✓ |
| `groundRoadCoverage` 的梯度门限（s0 / sx / sz） | `textureLod(…, 0.0)` | ✓ |
| `groundSampleImpl`（`sampleGround` / `sampleGroundAlbedo`，含火车远景、林缘阴影、碎浪） | `textureLod(…, 0.0)` | ✓ |
| `groundSampleAniso` 的缺瓦片回退 `min(A·2, 1)` | mip 平均后的 A | 有偏差，但有界：瓦片空洞边上「有路纹素 A ≈ 1」会把平均值抬高，缺失的过渡偏向「有影像」。只影响瓦片没取到时的边缘，而且远处才会用到高 mip。可以接受；按 §2 的 Worker mip 方案做完，这个偏差也就没了 |
| 城市灯点（`gh.wat.b` 夜光、`gh.alb.rgb` 判建成区） | 各向异性 RGB | ✓ 线性量，平均有意义，远处反而更稳 |
| `light-pollution` → `ground.nightSample` | 上传时在格心取水体 B（64² 网格） | ✓ 等价：格心的相对位置 (j·32+16)/2048 = (j·16+8)/1024 完全一致，更新时刻也和纹理同步（都在 `upload()` 里）。夜光在 Worker 里由 1024 双线性放大，数据本身约 500 m，没有损失 |
| CPU 端 `packRoads` / 聚落地毯 | 第 0 级像素 | 不受 mip 影响 ✓ |

`groundSampleAniso` 的光线微分（横向取水平方向，另一条轴在竖直面内，都投到过命中点、法线为 nT 的切平面上）推导正确；`|rd·n|` 的下限 0.02 合理。把 `terrainNormal` 挪进 `groundHit` 后，飞机和火车共用 `gh.nT`，改动一致。

- **最耗时**：定位爬行的来源。每个假设都要改一行、跑一次 flicker（每次约 1.5 分钟，大部分时间在等瓦片 `pending = 0`），一共跑了 7 次。如果 `dev-browser flicker` 支持 `--query`，能在不改代码的情况下覆盖 `GROUND_RES` / `FINE_MAX_RATE` / 道路 lod bias 这类常量（例如 `__voyage.ground` 暴露几个调试开关），这类归因审查能快一半。
