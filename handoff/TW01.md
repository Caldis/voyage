# TW01 · 让高耸对流云常见（只改天气场，零着色器）交接

分支：`worktree-agent-ab4606c29df5cde65`（已合并 master）。研究依据：`research/TOWERING.md` §1 与 TW01 一节。
用户原话：「似乎我没有见到那种横跨非常高海拔, 看起来非常 "高" 的那种云, 除非我选择特殊天气」。

## 改了什么

归属内三个文件，外加 README 坑点。**没有改着色器、名额（`MAX_STORMS = 4`）、摆放半径（280 km）、默认预设**。

| 文件 | 改动 |
| --- | --- |
| `src/weather.ts` `convection()` | 海上加两项：**夏季风槽** `monsoonTrough()`，范围 6–9 月、5–22°N、105–155°E，带季节内振荡的活跃期和中断期（2–3 周尺度的噪声）；**盛夏暖洋面** `warmOcean()`，范围 7–9 月、33°N 以南，季风槽里的部分不重复算。两项再乘 `(1 − 0.6·副高)`，日变化是清晨略强 |
| `src/weather.ts` `sample()` | 季风槽里信风积云的加分让掉 75%（西南季风区没有信风逆温）；暖洋面上浓积云得分加 `0.4·warm·conv` |
| `src/weather.ts` `stormSeed` | 砧顶跟着对流层顶走：急流轴（`JET_LAT` 按月）以南对流层顶 16.5 km、以北 11.5 km，砧顶 = 对流层顶 − 3~4 km + 0–1.8 km。飑线单体数改为 3–4 个，间距 10–22 km（按系统随机），每个单体沿线再错开 ±30%。另加 `stormSeed` 结果缓存（纯性能，确定性不变） |
| `src/weather-director.ts` | 新增纯函数 `pickStormSystems`，按「离视线近、看得见」挑名额：飞过去 40 km 以上的不挑；机头前方会被 `composeForWindow` 挪位的，按挪位后的位置算；另一侧窗外的不挑；正侧方到机尾之间的加 100 km 代价。`planStorms` 改用它，并且会把已经飞过去、看不见的系统撤掉，让出名额。`COMPOSE_AHEAD_KM` 抽成常量（值不变，60） |
| `scripts/weather-stats.mts` | 新增 `--only towering` 段（默认开，进门禁）：高耸对流统计表、「模型雷暴日」对照测站平年值、名额挑选新旧对照、飑线随机性，每个种子 26 条断言。新增 `--src <目录>`，可以对照改前版本的 weather.ts / weather-director.ts |
| `README.md` | 云坑点加 4 条（海上 0% 浓积云的根因、断言分不出的项要删、名额浪费、砧顶把外壳撑到约 17 km） |

**试过又撤掉的**（记在 README 坑点）：
- 近岸按周围陆地比例混入陆地午后对流：华南沿海午后浓积云只从 41% 变到 49%，改坏实验里没有一条断言失败，所以删了。
- 雷暴出生率上调一档：6 个种子都分不出来，撤了。

## 依据

- **[Johnson99]** Johnson et al. 1999, *J. Climate* 12:2397：热带对流呈三峰分布；在 COARE（西太暖池）观测里，浓积云占降水性对流云的一半以上；对流层顶约 16 km。
- **[HKO雷暴]** 香港天文台 1991–2020 平年值：雷暴日 1 月 0.23、7 月 7.97、8 月 8.90，全年 42.27 天。https://www.hko.gov.hk/en/cis/normal/1991_2020/normals.htm
- **[JMA那霸]** 气象厅那霸 1991–2020 平年值：雷日数 1 月 0.3、7 月 2.7、8 月 3.5，全年 20.4 天。https://www.data.jma.go.jp/stats/etrn/view/nml_sfc_ym.php?prec_no=91&block_no=47936 （本次抓取核对过）
- **「模型雷暴日」口径 [估算]**：当地 0–23 时逐时检查，单体边缘 20 km 内有单体，就算这一天是雷暴日。取 20 km 是因为雷声传 15–25 km [教科书]。这个换算有不确定度，所以门限放宽到平年值的 0.4–1.6 倍。
- 季风槽和暖洋面的范围与季节是 [教科书] 的定性结论，系数都是 [估算]，靠断言定下来。
- 砧顶：对流层顶高度与急流的关系是 [教科书]，差值 3–4 km 是 [估算]。

## 需要协调者知道的

- **默认开连续航程、默认浓积云，这两件没改**，是否开由用户决定。不开连续航程时，本任务的改动**看不见**（面板手选天气不走天气场）。
- **名额仍然不够**：华南内陆、南海盛夏午后 400 km 内平均约 5 个单体，最多二十几个，名额只有 4 个，摆放半径 280 km。远方一排塔要靠 TW02。
- **构图带没动**：`composeForWindow` 仍然把机头前方的系统挪到窗外 40–90 km，所以系统变多以后，塔都挤在同一个距离带上（TOWERING §4 的风险）。建议 TW02 一起处理，按远近分层。
- **性能**：雷暴出现的时间变多了（南海 / 华南沿海午后 400 km 内有雷暴的时间超过 90%），砧顶最高到约 16 km，外壳因此撑到约 17.8 km。连续航程里，「够得着雷暴」的帧比例会上升。PERF-15 已经记过 storm-graze ×1.38，建议波次收尾时性能工程师在连续航程南海午后测一次。回归场景不受影响：面板预设的雷暴固定 13.5 km，连续航程默认关。
- **海上雷暴的闪电频率**没区分海陆。海上对流的闪电远少于陆上 [教科书]，现在海上单体也是平均 5 秒一闪。这个不在本任务范围，建议另开一个小项。
- WX10 / WX11a / WX11a-b 的原断言在 6 个种子上全部通过（数值变化见「门禁」）。

## 开发体验反馈

- **哪里慢**：
  - 等测量锁约 20 分钟：截图前后两次排在别的代理的 `ab` / `flight` 后面。
  - 完整门禁每次约 3 分钟（比原来多约 20 s），跑了 3 次；改坏矩阵每轮约 4 分钟，跑了 3 轮。
  - 迭代时用 `--only towering`，单种子约 20 s，够用。
- **哪里卡**：
  1. 连续航程里截「窗外的塔」很难。导演一开，自动驾驶马上拐向下一段航线，坡度到 25°，窗外只剩海或者只剩天。`onJump` 摆雷暴要等变体编译，第一次调用只触发编译，要等约 15 s 再调一次。`playRate` 在关掉连续航程后不推进位置，想「往前飞一会儿等塔进窗」做不到。最后的做法是：摆好以后关掉连续航程、锁航向、把坡度改平，再把航向转到正对最近的单体（`handoff/TW01-scenes.json`）。希望 `dev-browser` 有一个场景字段，比如 `weatherJump: true`（自动等变体编译好再对齐天气场）和 `faceStorm: true`。
  2. `shots --only` 过滤不到 `--scenes-file` 里的场景，报「未知场景」，只能整份文件重跑。
  3. 在 worktree 隔离下，Bash 里 `bash -c "until …"` 和 heredoc 喂 python 都被拒。等后台任务只能用 PowerShell 的 while 循环或者 Monitor。
- **绕法与希望**：
  - weather-stats 加了 `--src <目录>` 对照改前版本（DX-27 的一半）；改坏矩阵收进了 `handoff/TW01-sabotage.mjs`（复制到 `src/tw01-sab/` 再改，不碰正式文件，也就不会再有 WX11a 那种「git checkout 冲掉未提交修改」的坑）。建议 DX-27 把两者合成一个正式工具，规则表放在各任务的 handoff 里。
  - `--src` 要求改前版本放在 `src/` 下的子目录，并且手动把导演文件里的 `./` 改成 `../`。如果能直接写 git 引用（例如 `--src master`）会更省事。
