# 云里棋盘纹「回归」调查（in-cloud 8.38 vs 2.56）

- 调查代理，只读：没改 src/，只写了本报告。测试页面用的是主工作区 master 的 dev server（5181，93b4d67 → 394e537），云步进片段和 resolve 都在页面内替换。
- 脚本与截图放在 `D:\Code\opus-test\tmp\incloud-inv\`，没有收进仓库：`rt.mjs`（在 `handoff/C03-rt.mjs` 基础上加了 `--offsets` 多姿态、`--phases` 多相位、`--natural` 自然实时、变体名 `@imm` / `~k`、resolve 空间平均补丁）、`variants.mjs`、`hf.py` / `summ.py`（指标）。

## 结论

1. **不是 C03 带来的系统性回归，是测法问题。** 8.38 和 2.56 / 2.63 来自不同次运行，姿态不一样。in-cloud 场景没有固定 `offset`，截图时飞机已经飞到 (0, 1.8–2.0) km，云场也在随墙钟演化。同一份代码在同一区域的 adj，换姿态就能从 0.4 变到 13.9；在默认姿态附近，只挪 150 m，old 就从 3.5 变成 9.3。跨次运行拿单帧 adj 相比，比较的是姿态，不是代码。
2. **同页、同姿态 A/B（C03-rt 实时路径）**：C03 对 adj 的影响随姿态变，范围是 ×0.72 到 ×2.25。16 个网格姿态上，几何均值 ×0.99、中位 ×1.01（相位平均后，final / old）；默认姿态附近 3 次分别是 ×2.25、×1.79、×1.01。TM01 碰到的恰好是默认姿态这个对 C03 不利的点，数量级本身没测错，但它不能代表云里的整体。
3. **C03 在云里确实有一个一致的代价：时间上的低频波动变大。** 16 帧块平均后的逐像素相对波动（relLow16），网格几何均值 old 0.87% → final 1.37%（+57%）；13 个姿态的另一轮是 0.96% → 1.63%。这就是 C03 审查预料到的「去相关后方差变大、偏低频」，在云里同样存在。relStd 差不多（7.3% → 8.1%）。
4. **根因：云里的 2×2 棋盘纹早就有，和 C03 无关。** 两个 1 spp 的随机源（步进位置 `jitter`、受光挑格点 `gDetailRnd`）打在一种对受光 od 极敏感的介质上（C01 注释已经写过这一点），`blend 0.12` 加 3×3 夹取的时间累积压不住。收敛后剩下的是抖动序列的**空间图样**：old 是细棋盘，final 是 IGN 转置带出来的对角条纹，见 `tmp/incloud-inv/win_*.png`（4 倍拉伸）。拆分诊断（下表）说明两个随机源单独固定哪一个都不够，两个都固定 adj 才降到 0.3。所以 C03 只是换了图样，噪声能量没变。
5. **推荐修法（零额外取样）**：在 resolve 里把已经读进来的 3×3 邻域顺手求和，本帧值按 `uCloudImmersion` 向 3×3 平均靠。实测在云姿态上 adj 几何均值 4.02 → **0.75**（最大 13.9 → 1.7），relStd 10.5% → 2.2%，relLow16 1.63% → 0.59%。云外 `uCloudImmersion = 0`，逐位不变。见文末「推荐改法」。
   只改 `gDetailRnd` 这一行（包括「云里退回旧序列」）都达不到这个效果，数字见「修法候选」表。

## 两种口径的区别

| | C01 返工 / TM01（`shots --freeze`、`TM01-measure --live`） | C03-rt 实时路径（本次主口径） |
| --- | --- | --- |
| 云缓冲怎么来 | 页面正常飞行、正常累积，冻结那一刻的历史缓冲（冻结后不再渲染云） | 冻结后手动推进云：blend 0.12 + 3×3 夹取，零运动，预热 96 帧、再推 128 帧，截稳态单帧 |
| 姿态 | 不可控：in-cloud 没写 offset，飞机位置 = 场景设定后飞过的距离（约 (0, 1.8–2.0) km），云场也在演化 | `--offset` 固定；同一页面里所有变体的姿态完全相同 |
| 相位 | 冻结时 `uFrame` 落在哪就是哪 | `frame` 清零后第 224 帧（相位固定，确定性），`--phases` 再多取几个相位 |
| 能不能换云着色器 | 不能（冻结时跳过云渲染，`--live` 模式也拒绝 march 补丁） | 能 |
| 适合做什么 | 看一眼当前画面 | 同页 A/B、时间波动 |

所以「C01 返工后 2.56 → 合并 C03 后 8.38」是**两次运行、两个姿态**之间的比较。它还叠加了一个巧合：默认姿态附近 C03 刚好偏差。以后判「云里棋盘纹回归」要用多个固定姿态做同页 A/B，报几何均值和最差值，不要用单个姿态的单帧。

另外，自然实时（`--natural`：解冻飞 3 s → 冻结截图，final / old / immOld 各 3 张）在同一个变体内部，adj 就在 0.4–11 之间跳，无法用来做 A/B（`n1/`）。

## 推荐改法

**首选：resolve 里的空间平均（`src/clouds/clouds.ts` 的 RESOLVE_FRAG，约 3 行，外加一个 uniform）**

```glsl
// 邻域循环里（已经在读这 9 个 texel，不加取样）：
    mn = min(mn, s);
    mx = max(mx, s);
    nsum += s;                     // 循环前：vec4 nsum = vec4(0.0);
// 循环后、重投影前：飞机在云里时，本帧值换成 3×3 平均（云里满窗是雾，没有需要保住的细节；云外 uCloudImmersion = 0，逐位不变）
  if (!depthHalf) cur = mix(cur, nsum / 9.0, uCloudImmersion);
```

在 `resolveMat.uniforms` 里加上 `uCloudImmersion: EXPOSURE_WHITEOUT`，和 marchMat 共用同一个对象（`clouds.ts:1163` 的做法）。

- 开销：9 次 vec4 加法、一次 mix，没有新增取样和分支（uniform 门控）。仍需实现者用 `passes.mjs` 在 in-cloud 上确认 resolve 的耗时。
- 效果：云里窗右下 adj 几何均值 ÷5.4，最差姿态 13.9 → 1.7。时间波动 relStd ÷4.8，relLow16 ÷2.8，比 C03 之前还低。
- 风险（实现 / 审查必须看）：
  1. **机翼边缘**：k = 1 以后棋盘纹没了，原来被噪声盖住的东西露了出来。一是更大尺度的淡对角条纹（4 倍拉伸才看得见）。二是机翼接缝 / 三角亮区边上的 2 px 阶梯，可能是半分辨率云缓冲在深度突变处的上采样本来就有的锯齿，也可能是 3×3 平均跨了深度边（`wingedge2.png`）。要用 64 帧真平均和单帧分别对比 final 与 k = 1 的机翼边。如果阶梯来自平均跨边，把 `uCurrentDepth` 的深度差加进权重（要多 9 次取样，不再零开销），或者退到 k = 0.5（adj ÷1.8）。
  2. 亮度 +1.3/255（208.7 → 210.0），在 1/255 量级上。
  3. 半进半出云时（immersion 按 0.5 s 平滑过渡），权重连续变化，没有跳变。
- 附带：C01 为了压云里的棋盘纹把 `CLOUD_MS_TAIL.y` 取到 2（注释写着「1 时棋盘纹仍略高于 master」）。有了空间平均，这个约束就没有了，可以按观感重新定（本次未测）。

**如果只允许动 `gDetailRnd` 一行**：用 immOld，云里逐位回到 C03 之前，云外逐位等于 C03 定稿：

```glsl
gDetailRnd = fract((uCloudImmersion > 0.5 ? jitter : ign(gl_FragCoord.yx + vec2(19.0, 47.0)) + uFrame * 0.41421356) + float(i) * 0.6180339);
```

它只收回 C03 在云里多出来的低频波动（relLow16 1.37% → 0.87%）。单帧 adj 平均不变（×1.06），棋盘纹本身不会消失。不建议把它当作棋盘纹的修法。

## 建议记入的坑点（给协调者，本报告不改 README / SOP）

- **in-cloud 的单帧 adj 高度依赖姿态**（同一代码 0.4–13.9，挪 150 m 能翻倍），场景表里 in-cloud 没写 offset，跨次运行不可比。建议给 in-cloud 加固定 offset（例如 `[-10, -5]` 这种噪声大、对变化敏感的姿态），判云里噪声用 ≥ 8 个固定姿态的同页 A/B 几何均值。
- 云里棋盘纹的根因是 1 spp 双随机源在高方差介质里的残差，修在累积 / 重建（resolve），不是修在随机序列：换序列只换图样。

## 开发体验反馈

- **最大的坑是姿态**：交接和 SOP 都把「实时单帧 adj」当成可以跨运行比较的数，但 in-cloud 没有固定 offset，飞机和云场都在动，同一份代码两次跑出来能差 2–3 倍。我花了一轮（3 个 offset）才发现 A/B 的结论随姿态翻转，后来改成 16 姿态网格才稳下来。希望场景表给 in-cloud 固定 offset，并在 `C03-rt.mjs` 里原生支持多姿态、多相位（本次的 `--offsets` / `--phases` 可以直接收进去）。
- **`realtime()` 是确定性的**（`frame` 清零），同一姿态重复跑结果逐位相同。这对 A/B 是好事，但一次截图只是 64 帧序列里的一个相位，需要 `--phases`。
- **测到一半页面被 HMR 刷新**：`gsp` 网格跑到第 13 个姿态时主工作区有提交，5181 的页面重载了（`Execution context was destroyed`），后 3 个姿态丢失。共用主工作区 dev server 做长测量时，建议协调者的提交避开，或者测量代理自起一个 detached worktree 端口。
- **`--natural` 自然实时对 A/B 没用**（同一变体内部 adj 就在 0.4–11 之间跳），只适合看一眼。
- Git Bash heredoc 里写 Python 替换 JS 源码，照例因为反斜杠失败，改用 Edit 才行（AGENTS 已记）。
