## 1. 剪枝等价性（乳状云，`clouds.glsl.ts`）：推导确认逐位不变

### `pouchField` 的第二个哈希提前退出

```glsl
float d2 = dot(fp, fp);
if (d2 >= 0.5625) continue;   // 0.5625 = 0.75²
vec2 h2 = stormHash22(id + o + 41.7);
float rad = 0.3 + 0.45 * h2.x;      // h2.x ∈ [0,1) ⇒ rad ∈ [0.3, 0.75)
float s = 1.0 - d2 / (rad * rad);
if (s > 0.0 && h2.y > 0.25) best = max(...);
```
`rad` 的上界是 0.75（`h2.x` 由 `fract()` 产生，严格小于 1，但用 0.75 做上界仍是保守的）。`s > 0` 要求 `d2 < rad² ≤ 0.5625`；反过来，`d2 ≥ 0.5625` 时无论 `h2` 取什么值，`s ≤ 0`，这个格子必然不贡献。跳过的判断只用 `d2`（跳过分支前就已算出，和原代码同一个变量），没有改变任何会被保留分支执行到的路径的浮点运算顺序——**逐位相同**，不只是"数值上不变"。

### `mammatusDensity` 的深度剪枝

```glsl
if (cl <= 0.0 || aBot + 0.1 - alt >= 1.26 * cl * zone) return 0.0;
float pd = max(pouchField(xz/1.4)*1.4, pouchField(xz/0.6+7.3)*0.6*0.8);
float depth = 0.75 * pd * cl * zone;
```
`pouchField` 单项贡献的上界是 `(0.4+1.2·1²)·0.75·1 = 1.2`（系数、半径、`sqrt(s)` 三者的最大值相乘），两级合起来 `pd ≤ max(1.2·1.4, 1.2·0.48) = 1.68`；`depth = 0.75·pd·cl·zone ≤ 1.26·cl·zone`。剪枝条件 `aBot+0.1-alt ≥ 1.26·cl·zone` 等价于「即使 `depth` 取到理论最大值，`pb = aBot+0.1-depth` 仍然 `≥ alt`」，而下游 `smoothstep(pb, pb+0.12, alt)` 在 `alt ≤ pb` 时恒为 0——两处推导都成立，验证通过。

## 2. 天气外壳空域跳跃（`clouds.ts`）：保守，未发现漏云

### 结构核对

- `CLOUD_STORM_SKIP` 只在 `defined(CLOUD_STORM) && !defined(CLOUD_TYPHOON)` 时定义，`laySeg`/`wxSeg` 的声明与跳跃判断整段都包在这个宏里；循环里唯一"泄漏"到 `CLOUD_WEATHER`（雷暴+台风共用）层级的是 `bool jumped = false;` 和 `emptyK` 公式里的 `jumped` 三元——台风变体里 `jumped` 声明但永远不会被置 `true`，`(i==0 || jumped ? 0.5 : 1.0)` 退化成原来的 `(i==0 ? 0.5 : 1.0)`，行为不变。default（无天气）程序完全没有 `CLOUD_WEATHER`，也不会引用 `jumped`。三个变体的预处理边界干净，没有找到会漏到不该改的变体里的代码。
- 半径界：`cloudRayWeatherSpan` 用 `R = c.z*7.5+0.5`，和密度函数 `stormDensity`/`stormDensityLite` 的提前退出 `dot(dd,dd) > c.z*c.z*56.0`（`√56 ≈ 7.483`）严格对应，7.5 比 7.483 大，再加 0.5 km 缓冲——保守。
- 高度界：`cloudRayWeatherSpan` 用 `[uShellBottom, c.w+1.8]`；`stormDensity` 的真实高度上限是 `top+OVERSHOOT+0.7 = c.w+1.6`——1.8 比 1.6 大 0.2 km 余量，保守。`uShellBottom`（1.2 km，等于 `STORM_BASE`）是全局既有的整壳下界，OCC_LAYERS 等其它代码早已依赖它覆盖雨幡到地面这一段，不是本次改动引入的假设。
- `laySeg` 处理了掠射视线"穿出层云底又在地面以外重新钻回层云"的第二段（`raySphere2(ro,rd,BOTTOM).x <= 0.0` 时把 `laySeg.y` 顶到 `outer(cloudTop).y`）：这段"洞"里没有层云是对的，跳跃逻辑仍会把它当作"在 laySeg 内"正常走 2dt 空白步，不会误跳——即报告自陈的"包络里夹着的空白照旧走 2dt"，代码与注释一致。
- `wxSeg` 是**多个雷暴的并集取外包络**（`min`/`max`），不是逐个雷暴的分段区间；两个雷暴之间如果有空当且不在 `laySeg` 内，会被"保守地"当作 wxSeg 内、按 2dt 正常走，不会被跳过——同样是保守，不是 bug，只是跳跃的收益在多雷暴场景里打了折扣（性能问题，不是正确性问题）。

### 我关心过的一个边界情况：`wxSeg` 单段假设 + 低空掠射

`cloudRayWeatherSpan` 里对每个雷暴只用 `cloudShellIntervalH`（返回单段"首次进入-首次退出"）与横向圆柱相交，**没有像 `laySeg` 那样处理"穿出该雷暴高度带的洞"**。理论上，低空贴近雷暴、视线在雷暴的圆柱范围内二次穿越 `[uShellBottom, c.w+1.8]` 高度带时，可能漏掉第二段。这正是 `storm-graze`（altitude 3 km 掠射）、以及我额外构造的 `squall-graze`（altitude 2.2 km、四个雷暴的飑线，专门用来压这个"多雷暴并集/二次穿越"假设）要测的场景。

## 开发体验反馈

- `dev-browser.mjs ab`/`gpu-ab` 共享同一把 `tmp/measure.lock`，本波并行开发的代理数量较多时排队明显（我这次 `ab` 排了近 2 分钟、`shader-budget --wait-quiet` 排队后 CPU 仍在运行中被推到 55~87%）。`--wait-quiet` 目前只在**开始前**等一次，测量过程中被其它代理的新任务顶起来的负载没法再等——建议 `shader-budget --baseline` 模式在每轮开始前都查一次 CPU，超阈值就跳过这一轮重测（而不是把污染的轮次也计入 min/MAD）。
- `cloudDump` 的 history 平均是在每次变体切换后独立跑 96(warm)+16(frames) 次 `R()`，但 `uFrame` 计数器（决定抖动相位）是页面级持久状态、不随变体切换重置，所以「old」和「cur」两次 dump 的抖动相位天然不同，导致原始 `.cloud.f32` 逐纹素直接相减不能用来判断"逐位不变"（哪怕是台风这种零代码差异的对照组，逐纹素相减也有 30% 的纹素超过 1e-4）。这一点交接文档里没写，我是先跑了台风对照组才发现的——建议在 README 或 `ab` 的帮助文本里补一句，免得下一个审查员重复踩。
