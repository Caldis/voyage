## 做了什么

新增一个可开关的调试小地图，画在左下角的独立 2D canvas 叠层上（不挡舷窗中心），默认关：

- 面板勾选「调试小地图」，或按 `N`（不在输入框里时）。
- 本机位置（图标固定在圆心，地图始终「航向朝上」）、已飞过的轨迹（按经纬度记录，按当前量程自适应间隔，最多 200 点）、当前航线（`director.leg` 的航段目的地，或没有连续航程时 `state.preset.dest` 的固定终点）。
- 「云的多普勒」：仿气象雷达回波图。背景网格（48×48）从 `director.weather.field.sample()` 按经纬度采样云量 / 云型换算出基础回波强度（绿→黄→橙红→品红→紫，仿雷达色阶），叠加**当前实际渲染中**的 `weather.storms` / `weather.hurricane`（不是另外查天气场的雷暴 / 台风列表）——这样不论天气是导演按天气场摆的、还是面板手选的（比如直接选「台风外围」预设），雷达图都和窗外看到的一致。台风的螺旋雨带是按角度做正弦调制、随半径衰减的近似图形，不是 `clouds.glsl.ts` 里真正的密度场（那边没有暴露 CPU 可读的接口，且不在本任务的归属文件里）。
- 远处的其他飞机（`traffic.ts` 的 `planes`，本来就是相对本机的公里偏移，直接旋到「航向朝上」即可，不用坐标转换）。
- 奇观（`wonders.active` 的经纬度 + 名字），量程内画真实位置，超出量程贴边缘 + 标真实距离（航线目的地用同一套「贴边缘」逻辑）。
- 图例（本机 / 轨迹 / 航线 / 交通 / 奇观的颜色对应）、色阶条、比例尺；点击地图本体在 50 / 200 / 800 km 三档量程间切换。

## 关键设计取舍

1. **雷达数据源 = 场（背景）+ 实际渲染（前景）而不是纯场**：用户原话要求「从 WeatherField 采样」，但 WeatherField 只在导演驱动的连续航程里才是「真正会被摆出来」的天气；面板手选天气（`weather.apply()`）完全绕开天气场。为了让第二张截图（台风附近）能不依赖连续航程复现，也为了雷达图不出现「窗外看不到的鬼天气」，背景云量 / 云型仍按用户要求查 `field.sample()`，但雷暴 / 台风的强回波核直接用 `weather.storms` / `weather.hurricane`（当前实际渲染的那一份）。代价：如果天气场里有一个「即将被导演摆出来但还没摆」的系统，雷达上看不到预告；这是有意的取舍（见 README 里的说明），不是遗漏。
2. **零开销**：`enabled=false` 时 `update()` 第一行返回；canvas 本身 `display:none`（浏览器不合成）。
3. **雷达网格分帧建**：48×48 网格若一帧算完，`field.sample()` 内部有好几次 `vnoise`/`hash`，实测虽然不至于是大尖峰，但为了稳妥仍按「每帧最多 4 行」分摊到约 12 帧（≈0.2 s），每约 800 ms 重来一次；建好之前继续显示上一份，不会有半张图的接缝。这个模式是仿 `clouds.ts` 的密度探针（「每 4 帧一次」）和 `ground/clipmap.ts` 的异步瓦片思路，不是本任务独创。
4. **不碰归属外文件**：`src/debug/minimap.ts` 除了 `../ground/geo`（`LocalFrame`，纯经纬度 ↔ 公里坐标换算，读它的导出）和 `../weather`（只取 `CloudRegime` 类型），不 import `traffic.ts` / `wonders/*` / `clouds/*`。main.ts 里把这几个系统的实时数据（`weather.storms`、`weather.hurricane`、`traffic.planes`、`wonders.active`、`director.leg`）转成小地图要的普通对象再传进去，`MinimapInput` 只依赖结构类型，不依赖这些模块各自的内部类型。
5. **验收口径**：性能自测用 `benchFrame(30)` 直接对照开 / 关小地图（而不是完整的 `dev-browser.mjs bench` 双端口批渲对照），因为这次改动没碰任何 WebGL 程序，唯一可能的开销来源是 2D canvas 合成 + JS 网格采样，用 rAF 批渲法足够看出「有没有意外的大头」；实测 2.26 ms/帧（开）对 2.18 ms/帧（关），差值在噪声量级（符合 DEV_SOP「测试的节制」：非逐像素路径改动不用上批渲双端口）。

## 已知的近似 / 局限

- 螺旋雨带是「看起来像螺旋」的正弦调制图形，半径 / 角频率是拍脑袋调的（`ang*3 - d*0.32`），不代表真实雨带的相位或强度分布。
- 网格是按「本机当前经纬度 + 航向」在建网格那一刻的快照，重建间隔内（≤ 0.8 s）本机若转弯，网格背景会和最新航向差几度——前景矢量元素（本机图标、轨迹、航线、交通、奇观）永远用最新数据，只有背景回波网格允许这点滞后。
- 轨迹目前存在内存里（不落盘、不跨会话），刷新页面后清空；这是调试工具，没有做持久化。
- 台风螺旋核心用 `weather.hurricane` 单点（中心 + 眼半径），没有单独画雨带的形状（真实雨带绕中心螺旋展开，这里近似成绕中心整体旋转对称衰减 + 角度调制），细节上和窗外画面的雨带走向不会逐一对应。

## 开发体验反馈

- **哪里慢**：`pnpm install` 忘了在新 worktree 里跑过——worktree 是从 master fast-forward 出来的干净检出，没有 `node_modules`，第一次 `typecheck` 直接报「tsc 不是内部命令」。以后接手一个新 worktree，先确认 `node_modules` 存在（或者干脆固定先跑一次 `pnpm install`，2–3 秒而已，比蒙一次报错再排查快）。
- **哪里卡**：`ImageData` 构造函数在当前 TS lib（`Uint8ClampedArray<ArrayBufferLike>` 的新泛型签名）下，普通 `new Uint8ClampedArray(n)` 类型对不上 `new ImageData(data, w, h)` 的重载，报的错信息绕了好几层（`SharedArrayBuffer` 相关）才看出是这个坑。以后遇到「`ImageDataArray` 类型不匹配」直接把字段类型标成 `Uint8ClampedArray<ArrayBuffer>`，不用纠结别的。
- **你怎么绕过去的，以及你希望有什么**：没有用共享 Playwright 浏览器锁，全程用私有 `chrome.exe`（`scripts/lib/chrome.mjs` 的 `launchBrowser` + `scripts/scenarios.mjs` 的 `applyScene`/`DEFAULTS`）自己拼了一个一次性验证脚本（`tmp/dx06-shots.mjs`，未提交）。`scenarios.mjs` 导出的 `applyScene` 只认场景表里预先写好的 `weather` 值，我需要的「召唤奇观」「切小地图量程」这类一次性调试动作不在场景表语义里，所以是直接在 `page.evaluate` 里操作 DOM（点击 `#wonder-summon`）和读写 `window.__voyage.minimap` 的（编译后是普通对象属性，TS 的 `private` 挡不住运行时）。如果以后还有「调试工具类」任务要反复验证「开关 + 状态 + 截图」的组合，一个通用的「小步骤脚本」（不是完整场景，而是像 `setPreset` / `clickById` / `setField` 这样的原子操作 + 组合）会比每次现写一个一次性 `.mjs` 省事。
