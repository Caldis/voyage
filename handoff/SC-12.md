## SC-2：`shader-budget.mjs`

新文件 `apps/voyage/scripts/shader-budget.mjs`，`package.json` 加了 `shader-budget` 脚本
（`pnpm --filter voyage shader-budget -- <参数>`，pnpm 会把 `--` 也透传给 node，`parseArgs` 对此是健壮的，已验证）。

### 原理

1. 用 vite `ssrLoadModule` 在 Node 里直接构造各材质（复用 `lint-shaders.mjs` 已经写好、已验证过的
   `collectPrograms`），不开浏览器，拿到全部 22 个程序的 GLSL 源码文本。
2. 私有 d3d11 headless 在一个 `about:blank` 页里，对每个程序的片元着色器调一次 `gl.compileShader()`：
   这一步只是 ANGLE 把 GLSL 翻译成 HLSL（编译器前端，很快，22 个程序总共约 1.2–2.2 秒），
   真正耗时的原生编译在 ANGLE 里是**延后到链接时才做**的，我们不链接，所以不会卡住，也不占 GPU。
3. ANGLE 翻译出的 HLSL 带 `@@ PIXEL OUTPUT @@` 等占位符（留给链接期生成），本地补全后交给
   Windows SDK 的 `fxc.exe`（`/T ps_5_0`）计时，各程序用一个小线程池并行（默认 `min(8, CPU核数-2)`）。
4. sampler 数直接数 HLSL 头里 `Texture2D<...> textures2D[n]` 这类声明的数组长度求和（比场景程序内的静态
   文本分析更直接、对所有程序统一生效，ANGLE 在 d3d11 上按类型打包数组，上限 16）。

为此把 `lint-shaders.mjs` 的 `collectPrograms`、`resolveIncludes`、`FRAG_PREFIX`、`INCLUDE_STUBS` 改成
`export`，并加了 `import.meta` 守卫（`main()` 只在直接执行该文件时跑，被别的脚本 `import` 时不会
自动触发一遍 `check:glsl` 再 `process.exit()` 把调用方一起杀掉）。`check:glsl` 的自测和完整检查都重跑过，
行为不变（见下面「验证记录」）。

### 用法

```bash
pnpm --filter voyage shader-budget                                   # 全部 22 个程序，/O1（默认，真实优化级别）
node scripts/shader-budget.mjs --only scene-default                  # 只测一个程序
node scripts/shader-budget.mjs --quick                               # /Od 跳过优化，全部程序几十秒内出结果
node scripts/shader-budget.mjs --bisect list                         # 列出已知的可换桩模块
node scripts/shader-budget.mjs --only scene-default --bisect ground  # 换桩 ground，自动带基线对照
node scripts/shader-budget.mjs --only scene-default --bisect "ocean-main;ocean-in-ground;ground"   # 分号=各自一个变体
node scripts/shader-budget.mjs --only scene-default --bisect "ocean-main,ocean-in-ground"           # 逗号=一起换桩
node scripts/shader-budget.mjs --jobs 4 --out tmp/screenshot/shader-budget.json
```

`--bisect` 的模块表（`MODULE_STUBS`）是照抄开发体验官 `variants.py` 的做法：按 `scene.ts` /
`terrain-shading.glsl.ts` **当前**的调用点文本做精确字符串替换，只对 `scene-default` /
`scene-ground-detail` 生效（其它程序会被跳过并提示）。代码演进后锚点会漂移——找不到就在输出里注明
「锚点对不上」，不会让整个工具报错退出，需要人工照着 `scene.ts` 当前的调用点更新 `MODULE_STUBS`。

### 验收：与浏览器真冷编译对照（要求 ≤15%，只需对比一个程序）

方法：先跑 `node scripts/dev-browser.mjs cold --port <端口>`（真冷启动，D3D11）拿到浏览器里
「场景着色器编译（后台）」的真实耗时，**紧接着**（不留时间间隙，减少系统负载漂移）跑
`node scripts/shader-budget.mjs --only scene-default`，用同一台机器同一时间窗口比较：

| 来源 | scene-default 编译耗时 |
| --- | --- |
| 浏览器真冷编译（`dev-browser.mjs cold`，D3D11） | **106514 ms** |
| 本工具离线预算（`shader-budget.mjs --only scene-default`，`/O1`） | **100811 ms** |

误差 = (106514 − 100811) / 106514 = **5.4%**，在 ≤15% 的验收范围内。

（过程中还有一次独立的方法学验证，用临时脚本对比过「真实页面 hook 出的完整文本」与「本工具实际用的
合成文本（`collectPrograms` + `FRAG_PREFIX` + `resolveIncludes`）」翻译出的 HLSL：两者字节长度完全一致
（128449 字节），确认合成文本这条路——不需要跑起来的 dev server——足够还原真实编译，这也是本工具最终
选择「不依赖 `--port`」这个设计的依据。）

## 坑

1. **`layout(location = 0)` 不写会导致 MRT 程序翻译失败**：`lint-shaders.mjs` 原来的 `FRAG_PREFIX` 只写
   `out highp vec4 pc_fragColor;`（没有显式 location）。`glslangValidator` 对此不报错，`check:glsl`
   一直没发现；但 `cloud-march` 自己额外声明了 `layout(location = 1) out highp vec4 outDepth;`，
   GLSL ES 3.00 规定一旦有多个片元输出，全部输出都要显式给 location，真实 ANGLE 编译会报
   `EXT_blend_func_extended` 相关错误。**已修**：`FRAG_PREFIX` 改成
   `layout(location = 0) out highp vec4 pc_fragColor;`（对单输出程序无影响，`check:glsl` 重跑过，
   22 个程序全部仍然通过）。这条建议写进 README 坑点——它说明「静态校验通过」不代表「真实浏览器编译
   一定过」，MRT 相关的坑目前没有任何工具能替代真实浏览器验证一次。
2. **JS 模板字符串里不能用反引号当「代码片段」引号**：第一次改 `FRAG_PREFIX` 时在字符串内部的注释里
   写了 `` `layout(location = 1) ...` `` 想强调这是代码，结果那个反引号提前闭合了模板字符串，
   后面的 GLSL 文本全部被当成 JS 代码解析，报 `SyntaxError: Unexpected identifier 'layout'`。
   以后往任何 JS 模板字符串（这里是拼 GLSL 前缀）里加注释，不能用反引号，只能用别的强调方式。
3. **`import.meta` 自动执行陷阱**：`lint-shaders.mjs` 原来在文件底部无条件调用 `main().catch(...)`，
   这对独立运行没问题，但一旦被 `shader-budget.mjs` `import { collectPrograms } from "./lint-shaders.mjs"`，
   会在 import 的瞬间自动跑一遍完整的 `check:glsl`（起 vite server、做语法校验），跑完还会
   `process.exit()` 把调用方一起杀掉。修法：`const isMain = path.resolve(process.argv[1] || "") ===
   fileURLToPath(import.meta.url); if (isMain) { main()... }`。以后任何脚本要被别的脚本 `import`
   复用逻辑，先检查它是不是也在文件底部无条件调用了自己的 `main()`。
4. **离线 fxc 计时对系统负载很敏感，同一份程序不同时刻测出的数字可能差 20%+**：本次交付过程中同一个
   `scene-default` `/O1` 先后测到 124917、111545、88587、100811、106514（浏览器）等不同数字，本机当时
   持续有其他代理占 GPU/CPU。**验收对照必须紧邻着测**（浏览器冷编译测完立刻测离线，中间不要插其它重活），
   不能拿不同时间点测的两个数字算误差——这条研究报告里已经写了（「只比较同一批里的数字」），这次交付
   过程亲身踩了一遍确认属实。
5. **fxc 计时不受 Git Bash 的 `MSYS_NO_PATHCONV` 坑影响**：研究报告提到 Git Bash 会把 `/O1` 之类的参数
   改写成路径，但那是**在 Git Bash 里直接敲 `fxc.exe /O1 ...` 命令**才会发生的问题；本工具用 Node 的
   `child_process.execFileSync` 调用 `fxc.exe`（不经过 Git Bash 的 argv 重写逻辑），已实测确认
   `/O1`、`/Od`、`/T` 这些参数原样传到 fxc，不用加这个环境变量。写进这里以免以后有人误加。
