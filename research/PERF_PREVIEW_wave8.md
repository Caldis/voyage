## 0. 结论先行

1. **当前帧预算（§1，[实测]）**：1600×1200 下晴天场景整帧 GPU 1.3–2.5 ms，160 Hz 预算（6.25 ms）很宽。**但用户的 3840×1950 画布上，晴天积云已经吃掉 86–90%**：noon-cumulus 5.37 ms、clouds-variety 5.64 ms，只剩 0.6–0.9 ms。夜城 7.45 ms（119%），雷暴 9.0 ms（145%），台风 15.5 ms（247%）。天气场景在用户机器上现在就靠自动档降档撑着。
2. **本波的余量就是用户分辨率下那 0.6–0.9 ms**。本文所有预算上限在晴天场景（noon-cumulus）上加起来约 +0.45 ms（用户分辨率），做完后大约 5.8 ms（93%），刚好放得下。天气场景没有余量：雷暴 / 台风类任务（TW03–TW05、C-TYPH、飞碟）的增量必须**同时附带抵消**，或者排在一次 PERF 优化之后。建议的抵消项是 C10b 审查留下的「refineOn 视线的层内细步只做到某个距离」。storm-sc-low（雷暴加浓层积云海）的云步进在 1600×1200 下就要 5.7 ms，是 storm-day 的 1.85 倍。
3. **TW01（已合并）的真实代价在着色器之外**：TW01 让连续航程里「够得着雷暴」成了常态（南海夏季午后超过 90%）。天气程序启用后 C10b 细步覆盖整个窗口，连续航程的典型帧从约 2.5 ms 变成约 4–7 ms（1600×1200）。回归场景看不出这一点，要进 PERF-15 实测。
4. **逐条建议（预算上限见 §3，可以直接粘进简报）**：
   - **做，且几乎免费**：WX11g-b 低风速耀斑（改泊松闪点公式，≈ 0）、#9 海天暗墙、远海横纹、暗尾迹（先查因）、城市灯光照低云（折进已有的 `eBelow`，由 CPU 算 uniform）、飞碟（雨幡只吸收，不接受单次散射）。
   - **做，小成本**：C13 便宜版（resolve 内 3×3 联合双边，不增加取样）、#7 整流罩 + #11 机身影子 / 小翼（合成一个机翼任务，FXC ≤ +5%）、#10 倒影、#8 大风海面、TW05、TW06。
   - **做，有成本要看住**：C06（近云场景云 pass +8–20%，按像素足迹淡入，不按画质档分档）、TW03（掠射视线可能 +15–40%，要在层上部放宽步长）。
   - **改方案后做**：**TW02** 远景塔层要做成独立小程序并用 scissor 只画地平线带，雷暴名额**不扩**（扩了雷暴云 pass +20–50%）。**TW04** 如果砧照原样放大 2–5 倍，覆盖面积会 ×4–25，雷暴天整帧 ×1.3–2，所以外缘改成「砧盾」层状密度。**C-TYPH** 让卷云盖变薄会让视线走得更远，要限制盖下的步数。
   - **本波不做**：TW07；WX12（多层云，派发前单独预审，估算云 pass +30–80%）。
   - **事后上限**：C-FLAT 性能上免费（噪声内、FXC −7.5%），但时间噪声 ×1.8–2.6，这笔账转给 C13；C-TOFU 云 pass ≤ +5%（掠射 ≤ +8%）；W-EDGE 机翼 FXC ≤ 5.3 s，且机翼编好要比窗外早 ≥ 1 s。
5. **冷编译**：关键路径仍是窗外程序。本波碰窗外的六项累计上限是 13%，贴近一波 15% 的门槛，**本波不能再往窗外加东西**。雷暴变体按上限累计会到约 +33%（约 5.5 s），超出本文定的 5 s，所以 TW03 / TW04 / TW05 不要同一波做完（§4.1）。
6. **画质档**：一条都不建议做着色器分档，理由是变体数会翻倍。近处细节一律按像素足迹淡入，低档的 `cloudScale 0.5` 会自动少算。
7. **执行顺序**（性价比，§4.2）：（先派一个 PERF 压 storm-sc-low，给雷暴类美术项腾抵消）WX11g-b → 海面三项查因 → C13 (a) → 城市灯光 / 飞碟 → 机翼合并任务 → 倒影 / 大风海面 → TW02 → C06 → TW03 → C-TYPH + TW04 → TW05 / TW06。

## 1. 当前帧预算（[实测]，master 3bfb9d6，5181）

**口径**：`scripts/passes.mjs` 的一个本地副本（`tmp/pp8/passes-vp.mjs`：只加了视口 / DPR 参数、测前固定「高」档、打印渲染器），`EXT_disjoint_timer_query_webgl2` 按 pass 计时，30 帧 × 3 轮，**每帧 ms = 中位 × 调用数 ÷ 帧数**。均值被少数被抢占的查询拉高，所以用中位。渲染器是 `ANGLE (NVIDIA RTX 5090 … D3D11)`，硬件渲染，不是 WARP。两种分辨率画布分别是 1600×1200 和 3840×1950，都核对过。

读法：
- **分辨率倍率不是 3.9**。画布像素是 3.9 倍，但窗外和云只算舷窗孔径以内的部分，宽屏下孔径占画布的比例更小，所以窗外、云步进、机翼约 ×2；舱内合成与云 resolve 按整幅画布算，约 ×3.2–4。**给用户分辨率做估算时，窗外 / 云 / 机翼的增量 ×2，舱内 / resolve / 新的全屏 pass ×3.5–4。**
- **用户机器上，晴天积云只剩约 0.6–0.9 ms**。夜城已经超出预算，雷暴和台风更多。天气场景和夜城在用户那里靠自动档降档（PERF-5：强天气先降档，云缓冲变成 3/4 或 1/2）。这不是本波新引入的问题，但说明**不存在「GPU 还很空」的余地**。
- **晴天场景最大的单项是机翼**（1600×1200 下 0.83 ms，用户分辨率 1.63 ms），比云步进还贵。PERF-3 留下的「机翼步数 128 → 96」一直没做，这是给美术腾余量最直接的一刀，建议排进 PERF-15 之后。
- **storm-sc-low 是非台风里最贵的视线**：云步进 5.7 ms，是 storm-day 的 1.85 倍，比 C10b 审查记的 storm-graze（3.67 ms）还贵。这是「雷暴程序 + 浓层积云海 + C10b 层内细步」叠在一起的结果。TW01 之后连续航程里这种画面会常见，是本波最值得先压的一处（§4.2 第 0 条）。

## 2. 通用条款（每份美术简报都要带上）

1. **帧预算口径**：用户的屏幕是 160 Hz（6.25 ms/帧）、2560×1300 视口 × 1.5 DPR（画布 3840×1950，是 1600×1200 的 3.9 倍像素），高档画质 `cloudScale = 1`、`dprCap = 1.5`，所以用户实际画的就是 3840×1950 全分辨率。验收一律用 `dev-browser gpu-ab`（8 轮 ABBA + 一个 A/A 变体）在 1600×1200 上量相对增量；绝对值按 §1 的倍率换算到用户分辨率。
2. **集显折算**（[引] C10b 审查 §4）：5090 对 Iris Xe / M1 约 30–45 : 1。集显会自动落到「低 / 最低」档：云缓冲 `cloudScale 0.5`（像素 1/4），最低档 DPR 封顶 1。所以**云类 pass 的增量 × 8–11、全分辨率 pass（窗外 / 舱内 / 机翼）的增量 × 30–45** 就是集显同分辨率下的量级。
3. **冷编译**：当前启动关键路径是**窗外程序**（真冷约 7.5 s，[引] PERF-WING §1），机翼约 5.3 s（加 W-EDGE B′ 约 5.8 s），舱内约 4.7 s，座椅约 1.6 s，默认云程序约 0.8–1.0 s。
   - **碰窗外程序（`outside-default`，海面 / 地面 / 天空 / 交通 / 闪电）的任务**：直接加在关键路径上，单任务离线 FXC ≤ +3%（不是 10%——这一波已有多项要碰它，见 §4 的累计表），不新增 sampler（窗外 14/16，余 2 个留给真正需要的）、不新增循环、不新增重函数调用点。
   - **碰机翼程序的任务**：机翼离关键路径只剩约 1.7 s（[引] PERF-WING §5，B′ 之后）；单任务 FXC ≤ +5%，且真冷启动「批次各程序编好」里机翼要比窗外早 ≥ 1 s。
   - **碰云程序的任务**：默认云程序离关键路径很远（0.5 s 对 7.5 s），可以按 SOP 的 10%；但**雷暴变体**（离线约 4.1 s）在 TW01 合并后变成连续航程里的常态程序（南海 / 华南夏季午后 400 km 内有雷暴 > 90%，[引] TW01.md），它编不好雷暴就不能出现，所以雷暴 / 台风变体单任务也按 ≤ +10%，绝对值雷暴 ≤ 5 s、台风 ≤ 8 s。
   - **新程序**一律首帧后后台按需编译，不进启动批次。
4. **不按画质档出着色器分档**（[引] C10b 审查 §2(c)）：`quality.ts` 的档位只改 `cloudScale` 与 DPR，着色器分档会让云变体数翻倍（冷编译、预编队列一起翻）；用 uniform 分档则自动档升降时整窗跳。**替代做法**：所有「近处细节」按**像素足迹**淡入——低档 `cloudScale 0.5` 时足迹自动变大一倍，细节自然少算，不需要任何档位开关。
5. **云步进循环里不加「平时不走」的分支**（[引] README 硬约束：W00 实测加一段不走的分支让整体步进慢一倍）。夜间、雷暴、台风才有的东西：①能折进已有的 uniform 就折进 uniform（CPU 算好，着色器零新代码）；②不能的写进已有的 `#ifdef CLOUD_STORM / CLOUD_TYPHOON / CLOUD_WEATHER`。
6. **受光步进（6 / 8 步的小循环）里不加密度调用**：它套在主步进循环里，每多一次 `cloudDensityLite` 就是「每个有云样本 ×1」，量级 +10–20%。
7. **不许悄悄变贵的「让云变薄」**：云变透明后视线要走得更远、步数更多（被挡住的视线原本早退）。凡是让大面积云变薄的改动（台风卷云盖、砧外缘、雾海），验收要带 `ab` 的 `cloud-steps` 诊断，步数上限 384 的撞线比例不许上升。

## 3. 逐条预审

每条的格式：影响的 pass / 程序 → GPU 增量（5090 实测或估算 + 集显量级）→ 冷编译风险 → CPU / 内存 / Worker → 是否分档 → 建议 → **预算上限（可直接粘进简报「验收」）**。
云步进的基线（1600×1200，5090，高档，§1 [实测]）：noon-cumulus 0.50 ms、sea-sc 0.34、clouds-variety 1.8–2.9、night-city 1.56、storm-day 3.08、storm-sc-low 5.69、typhoon-bands 6.24；未实测的沿用上游：cu-side 1.73、graze-sc 1.10（[引] C10c 审查 §3）、storm-graze 3.67（[引] C10b 审查）。机翼 0.6–0.9 ms，窗外 0.5，舱内 + 座椅 0.34。换到用户分辨率时，窗外 / 云 / 机翼约 ×2，舱内 / resolve / 全屏 pass 约 ×3.5–4（§1.2）。

### 3.1 已派 / 在做的（给事后上限）

#### C-TOFU（ART-8 #1 豆腐块；在做，分支 fa9f089）

#### C06 近处云第二级细节（ART-8 #3 后半；与 TW04 共用做法）

- **影响**：主步进的完整密度 `cloudDensity`（只该在这一处）。
- **GPU**：多一次细节噪声 `textureLod`（复用 `uDetailNoise`，更高频的坐标），只在「近处 + 已在云里 + 像素足迹小于细节尺度」时取。近云为主的场景（cu-side、noon-cu-close、backlit-close、in-cloud）有云样本多数在近处，**[估算] 云 pass +8–20%**（cu-side 1.73 ms → +0.15–0.35 ms；用户分辨率约 ×4 → +0.6–1.4 ms）；俯视远云（noon-cumulus、sea-sc）几乎不触发，+0–3%。集显低档：足迹变大一倍，触发范围缩到约一半，[估算] +1–2 ms。
- **冷编译**：新纹理采样在主步进循环体内，**[估算] cloud-march FXC +3–8%**；**不能进 `cloudDensityLite`**（受光 6 / 8 步 × 每个有云样本、云影图、探针、占据网格），否则开销和编译都乘好几倍。雷暴变体若共用（TW04 的小卷团），storm FXC 另算。
- **分档**：不分档；**按像素足迹淡入**，低档自动少算（§2 第 4 条）。
- **建议**：**做，排在 C13 之后**（先把噪声压下去，才看得出新细节是细节还是砂粒），与 TW04 错开同一波。
- **预算上限**：「`gpu-ab --time clouds`：cu-side / noon-cu-close / backlit-close ≤ +12%，in-cloud ≤ +15%，noon-cumulus / sea-sc / clouds-variety ≤ +3%；离线 FXC cloud-march ≤ +8%；cloud-shadow-map / cloud-probe / cloud-occupancy 预处理后与改前逐字相同（新细节只在主步进）；不新增 sampler；细节按像素足迹淡入（低档自动减少），不做画质档开关。」

#### WX11g-b 低风速海面耀斑椒盐点（ART-8 #4）

- **影响**：窗外程序 `oceanRadiance` 的耀斑段（关键路径）。
- **读代码的发现**：椒盐点不只是「粗糙度没按足迹加宽」。`ocean.glsl.ts` 的耀斑乘了一个**泊松闪点**（`sparkle`）：`λ = 5·足迹面积·exp(−tan²/σ²)`，λ < 4 时每个格子要么亮 `1/pHit` 倍、要么全黑——低风速时 σ² 很小，耀斑区大部分像素 λ < 1，就成了孤立的亮点；格子每 1/8 s 换一次随机数，所以**飞行中一定闪**。修法是这段公式（λ 的下限、σ² 按足迹加上 Toksvig 类的未分辨方差、或近处 λ 大时直接取期望），全是算术。
- **GPU**：**[估算] ≈ 0**（< 0.005 ms）。
- **冷编译**：几条算术，不加循环、不加采样。**[估算] outside-default FXC ±2%**（噪声内）。
- **建议**：**做，最先做**（锯齿 / 闪烁是最高优先级缺陷，且最便宜）。
- **预算上限**：「离线 FXC outside-default ≤ +2%（与 master 交替 ≥ 4 轮）；low-sea-glint / sea-calm-low 整帧 GPU ≤ +1%；不新增 sampler、循环、函数调用点。」

#### C-STORM-SAUCER 黄昏 / 月夜雷暴云底「飞碟」 + TW-NIGHT 月夜塔身黑白横带 + 砧上沿点列（ART-8 #5）

- **影响**：`CLOUD_STORM` 变体的主步进受光段（雨幡、塔身）。
- **飞碟的两种修法**：
  - 「雨幡在受光密度里补自遮挡」= 在 8 步受光循环里给 `cloudDensityLite` 加雨幡：**每个有云样本多算 8 次雨幡密度**，**[估算] 雷暴云 pass +5–15%、cloud-march-storm FXC +5–10%**。不推荐。
  - 「雨幡只吸收、不接受太阳单次散射」（或按解析的塔身遮挡把雨幡的单次散射乘掉）：去掉一项，**[估算] ≈ 0 或略快**。推荐。
- **TW-NIGHT**：月夜环境光量级 / 多次散射下限 / 自阴影柔化。前两个是公式（在已有的环境光与多次散射项上改权重，≈ 0）；「自阴影柔化」若是加受光步数或多取一次密度就贵（同上 +5–15%）。先用 `ab` 开关定因（BIS-8 已排除 C10c 回归）。
- **砧上沿点列**：先用 `cloud-steps` 看是否撞步数上限 / `uLoopGuard` 截断。**如果修法是「雷暴程序步数上限 384 → 更高」**：只影响撞线的像素，但 storm-graze 这类视线本来就贵，**[估算] storm-graze +5–20%**；优先改「砧内步长随密度自适应」。
- **冷编译**：全部在 `CLOUD_STORM` 里，默认程序不动。
- **建议**：**做（飞碟用吸收版、TW-NIGHT 先定因）**，可并入 TW05。
- **预算上限**：「storm-day / storm-sc-low / storm-graze 云 pass 各 ≤ +3%（飞碟 + TW-NIGHT 合计）；离线 FXC cloud-march-storm ≤ +5%；受光步进循环里不新增密度调用；默认云程序预处理后逐字不变。」若砧点列要提高步数上限，另加：「storm-graze 云 pass ≤ +10%，绝对值 ≤ 4.2 ms @1600×1200」。

### 3.4 TOWERING 的 TW02–TW07

#### TW02 远景对流塔层（280–750 km）+ 名额

- **影响**：一个**新程序**（解析求交，不走体积步进）；导演的远 / 近交接；`MAX_STORMS` 4 → 6–8（研究的建议）。
- **GPU（远景层）**：地平线 ±3° 的视线带只占窗户竖直视场（约 35–40°）的约 15%；每个像素对 ≤ 16 座塔求「椭球 + 透镜」解析交、半球明暗、查空气透视 LUT。**用 scissor 只画地平线带**，[估算] **0.03–0.08 ms @1600×1200**（用户分辨率 0.1–0.3 ms），集显 +1–3 ms。TOWERING 给的 ≤ 0.3 ms 偏松，收紧。
- **合成方式决定冷编译风险**：
  - 塞进窗外程序：窗外是关键路径且 sampler 14/16，**不许**。
  - 塞进云步进做新变体：变体键组合（默认 / 卷云 / 奇观 / 雷暴 / 台风）会翻倍，**不许**。
  - **推荐**：单独的小程序、首帧后后台编译，结果以「在云后面」的方式并入云缓冲（远塔在 280 km 外，必在本帧所有云之后：`raw.rgb += (1 − raw.a)·T·塔`，用 `ONE_MINUS_DST_ALPHA, ONE` 的混合画进 raw，零新 sampler；raw 是 MRT、浮点混合要 `EXT_float_blend`，不便时退一步给 resolve 加一个输入，resolve 的 sampler 富余）。空气透视超出 LUT 400 km 的部分在这个程序里自己算。
- **名额 4 → 6–8：不建议**。雷暴密度里 `for (i < uStormCount)` 按单体逐个算（`clouds.glsl.ts` 1036 / 1074 行），「够得着雷暴」的视线上每个样本的开销随单体数线性涨；**[估算] 雷暴场景云 pass +20–50%**，storm-graze 可能 > 5 ms。远处的单体交给远景层，体积名额保持 4。
- **CPU**：导演多管一类「远景塔」列表，≤ 16 个，每帧上传一次 uniform 数组，可忽略。
- **建议**：**改方案后做**：远景层用独立小程序 + scissor；名额不扩。
- **预算上限**：「远景层 GPU ≤ 0.08 ms @1600×1200（tw-far-row 场景），不在启动批次里（首帧后后台编译），离线 FXC ≤ 1.5 s；窗外程序与所有云步进变体预处理后逐字不变；不新增窗外 sampler；`MAX_STORMS` 保持 4（要扩另审）；远 / 近交接帧 `ab live` 跳变 < 噪声底 ×2。」

#### TW03 积云云顶分布与「冲出云层的塔」

- **影响**：`weather.ts` 云型参数（浓积云层顶放到 8–10 km）、`clouds.glsl.ts` 剖面参数化（C-TOFU 之上）。
- **GPU**：层变厚 = 擦云层的视线在层内走得更长。晴天积云 1.2–3.4 km → 浓积云层 1.4–10 km，层厚 ×3–4。俯视时只多几个有云样本；**低空 / 同高度掠射时，层内细步（C10b：60 km 内空白步也走 dt）的步数随层厚成比例涨**。[估算] tw-towering-noon +5–15%，tw-towering-low 与 graze 类 +15–40%，可能撞 384 步上限（撞了就远处截断，画面缺云）。
- **冷编译**：只改参数 ≈ 0；若新增「秃积雨云」单体种类，放进 `CLOUD_STORM`（+3–8% storm FXC）。
- **建议**：**做，C-TOFU 后**；层顶提高只对浓积云云型，普通积云不动；层内空白步在层上部（只有少数塔的高度）放宽成 2dt。
- **预算上限**：「noon-cumulus / clouds-variety 云 pass ≤ +3%（普通积云不变）；tw-towering-noon ≤ +10%，tw-towering-low 与 graze 类浓积云视线 ≤ +20%；`cloud-steps` 撞 384 步比例不上升；新单体种类只进 `CLOUD_STORM`，storm FXC ≤ +8%。」

#### TW04 积雨云几何与质感重做

- **影响**：`CLOUD_STORM` 变体的 `stormDensity` / `towerShape`，占据网格范围。
- **GPU（本条最大的性能风险）**：**砧放大 2–5 倍 = 砧覆盖的天空面积 ×4–25**。现在砧 10–36 km 宽，大部分视线「够不着雷暴」走快路径（T33 的包围盒）；砧变成 50–150 km 后，窗里大片视线都要穿过砧的包围盒、逐样本算 `stormDensity`。**[估算] storm-day / storm-sc 云 pass ×1.3–2.0**，storm-graze 可能到 5–7 ms（1600×1200）；用户分辨率上雷暴天会掉出 160 Hz。塔身三级隆起（多一级 0.3 km Worley）+5–10%。
- **冷编译**：[引] TOWERING §4：`stormDensity` 内联 4 处，T03 时 +30%。规矩：完整版只在主步进一处；受光 / 云影 / 探针 / 占据网格只用 Lite。
- **CPU / 内存**：占据网格 ±128 km；砧 150 km 时要扩范围或降格子精度（保持显存不变）。
- **分档**：不分。
- **建议**：**改方案后做**：①砧的外缘（离塔心 > 2R）不走逐单体 SDF，改成一张「砧盾」层状密度（像卷云层一样按 2D 覆盖率 + 高度剖面，一次取样，多单体共用一片），只有塔身与砧根走完整 `stormDensity`；②远处（> 150 km）塔只留两级隆起、mip 封顶与 C-TOFU 同一套；③包围盒快路径随砧盾一起重做。与 C06 错开同一波；与 C-TYPH 同一个代理。
- **预算上限**：「storm-day / storm-sc / tw-storm-far150 云 pass ≤ +15%，storm-graze ≤ +15% 且绝对值 ≤ 4.2 ms @1600×1200（`gpu-ab` 8 轮带 A/A）；离线 FXC cloud-march-storm ≤ +10%（≤ 4.6 s），cloud-shadow-map-weather / cloud-probe-weather / cloud-occupancy 各 ≤ +10%；完整 `stormDensity` 只有主步进一个调用点；占据网格显存不增加。」

#### TW05 塔的受光与大气透视

- **影响**：`CLOUD_STORM` 受光段。
- **GPU / 冷编译**：①塔顶按高度取透射率：`keyLight(r, …)` 若已按高度取则 ≈ 0；②塔间长影：若靠「受光步进更长」→ 加步数就是 +10–20%，**不许**；靠云影图（已有）或把 8 步的最后一步拉长（步数不变）≈ 0；③塔底暗、雨幡暗幕：公式；④飞碟：见 3.3；⑤远塔被霾吃掉塔脚：空气透视已按距离做，加一项边界层霾的高度遮罩，≈ 0。

#### TW06 对流生命周期（= WX14）

- **影响**：天气场（CPU）、雷暴变体加阶段量（uniform）、占据网格重建节流。

## 开发体验反馈

- **哪里慢**：测量锁排队约 35 分钟。前面有一个 5 轮的 `shader-budget` 和两个 `ab`。
- **哪里卡**：`passes.mjs` 没有视口 / DPR / 画质档参数，要量用户分辨率只能复制一份改；它拿不到锁时只警告不等（`acquireOrWait` 等 20 分钟超时后也会不持锁继续），第一轮两种分辨率和别的代理的 `ab` 并行，数据被污染（均值被拉高 30–100%，中位基本还稳）。
- **怎么绕的**：副本里改成 `acquireOrWait`，用中位数换算每帧 ms，同一套场景跑两次对照。
- **希望有**：`passes.mjs --viewport --dpr --quality high`；`passes` / `gpu-ab` 的输出里带「这次是否持锁」字段；`gpu-ab` 支持 `--viewport`，用户分辨率的增量就能直接做配对对照。
