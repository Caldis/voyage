# 性能报告 · 第 3 波收尾（性能工程师，2026-09-27）

主分支 `cfcb036`，开发服务器 5181。硬件：RTX 5090，ANGLE d3d11（`dev-browser.mjs` 默认口径），视口 1600×1200、DPR 1。
只读 + 测量，未改 `src`。临时脚本都在主仓库 `tmp/perf/`（见文末「测量方法与脚本」）。

## 零、结论先行

1. **帧时间**：13 个回归场景的 GPU 时间在 1.3–2.9 ms 之间；**雷暴 7.3 ms、台风三场景 8.6–8.8 ms 是唯一的热点，其中 81–87% 花在云光线步进上**。在 1600×1200 的 5090 上所有场景都远低于 16.7 ms，但换到 1.5 倍屏（实际绘制 2400×1800）时台风到 17.1 ms，已经掉出 60 fps。
2. **冷启动**：无负载时 d3d11 真冷启动 **26.6–27.0 s**（SC-3 前 84–117 s，SC-3 后约 31 s）。其中 **4.8 s 是一次可以消掉的重复编译**：见第 3 条。
3. **「首次 render 同步卡 3–5 s」的根因已经坐实**（SC-4 遗留问题）：**云光线步进程序是 MRT（两路输出：颜色 + 深度）。在 ANGLE/D3D11 上，MRT 程序并行链接完成后，第一次 draw 还会同步地把整个像素着色器再编译一遍**（4.9 s，等于 march 一次完整 FXC 编译的时间）。改成单输出，这笔开销就没了（1 ms）。链接时绑什么帧缓冲都没影响。证据见 §3.2。
4. 机翼 pass 有一半开销（0.30–0.47 ms）花在边缘超采样上，而超采样只落在 0.17–0.43% 的像素上。写法低效，能省 0.2–0.35 ms。
5. 场景 pass 一直是 0.84–1.09 ms，与视角、关不关遮光板都基本无关。其中约 75% 花在 `outsideRadiance` 上，舱内部分只占约 0.1–0.25 ms。T06 提到的座椅视角 +13–17%，折成绝对值只有 +0.05–0.09 ms，不算热点。

### 3.2 「首次 render 同步卡 3–5 s」：根因与证据

**我的判断：这不是「批次之后任意一次 render 都有的结算开销」（SC-4 的推测），而是 ANGLE/D3D11 对 MRT 程序的一次重复编译。** 链接时，ANGLE 生成像素着色器用的是「默认输出布局」，只含着色器的第一个输出。云光线步进同时写 `gl_FragColor` 和 `layout(location = 1) out outDepth`，第一次真正 draw 到双附件帧缓冲时，输出布局对不上，ANGLE 就在 GPU 线程上同步地把整个 march 像素着色器重新编译一遍。之后的程序缓存会把这个变体也存下来，所以热启动时看不到这一下。

证据链：

1. **逐调用计时**（`tmp/perf/stall.mjs`，在真冷启动里给每个 WebGL2 调用计时）：批次结束后，march 的 `getProgramInfoLog` 只要 1 ms，紧跟着 resolve 的 `getProgramInfoLog` 卡了 4859 ms。在每个 draw 后面插一次同步的 `getError()` 以后，卡顿准确地落到 **march 的第一次 `drawArrays` 上（4772 ms）**。resolve、FFT、场景、机翼的第一次 draw 都在 0–1 ms。SC-4 看到的「卡在谁身上都一样」，其实是「卡在 march 首次 draw **之后**的第一个同步调用上」。
2. **批次里只有 march 是 MRT**：`hdr` / `hdrWing` 都是单附件（`main.ts:81/90`）。`main.ts` 里「场景画进两张目标（MRT）」的注释已经过时。
3. **最小复现**（`tmp/perf/mrt-real.mjs`，在 about:blank 里用从应用抓到的**真实 march 源码**，nonce 破缓存，`KHR_parallel_shader_compile` 轮询到完成后再计时首次 draw）：

   | 变体 | 并行链接 | 首次 draw | 第二次 draw |
   | --- | ---: | ---: | ---: |
   | B：MRT，链接时绑双附件 FBO + `drawBuffers=[0,1]`（three.js 现状） | 4742 ms | **4909 ms** | 0 |
   | C：MRT，链接时绑默认帧缓冲 | 4675 ms | **4902 ms** | 0 |
   | A：同一着色器改成单输出（`outDepth` 降成普通变量） | 4700 ms | **1 ms** | 0 |

   **首次 draw 的卡顿 ≈ 链接时间，所以是完整重编；链接时绑哪个目标没有影响（B = C）。** 因此 `main.ts` 里「各自绑定真正要画进去的目标再发起编译」这个做法，对 MRT 没有作用。对单输出程序也没必要，但它无害，可以保留。
4. 复现时踩过的坑：多个不同类型的 sampler 默认都指向纹理单元 0，或者采样的纹理正好挂在当前帧缓冲上（反馈环），draw 会被 WebGL 校验直接拒掉（`INVALID_OPERATION`），根本走不到 D3D，**看起来就像「不卡」**。所以复现脚本一定要检查 `getError()`。

修法见 PERF-1。预计收益：冷启动 **−4.7 s（27 → 约 22 s）**，同时消掉启动期唯一一次 ≥1 s 的主线程冻结（这正是 SC-4 没达成的验收项）。

后续可以做的验证（如果有人想坐实 ANGLE 内部机制）：`chrome://tracing` 抓 `gpu` / `disabled-by-default-gpu.angle` 类别，在卡顿的 4.8 s 里应该能看到 `ProgramD3D` 的 `getPixelExecutableForCachedOutputLayout` → `D3DCompile`。

### 4.2 热点 1：雷暴 / 台风的云光线步进（5.9–7.6 ms，占整帧 81–87%）

**根因**：
- 有雷暴或台风时，云壳上沿抬到雷暴顶 / 台风顶（十几 km）。巡航高度 10.7 km 的相机就在壳里，**几乎每条视线都要从 0 走到 60 km（`AERIAL_MAX_DISTANCE`），最多 256 步**。
- 每一步都要调用完整的 `cloudDensity`：雷暴是主塔 SDF、3 个伴生塔、砧、雨幡、乳状云；台风是 `hurricaneDensity`。**唯一的剔除是一个粗圆（雷暴 `R²·56`；台风 `r > 18·Re`）**。台风的剔除圆几乎盖住整个画面，所以远处的空气里每一步都在付完整台风密度的钱。
- 此外，每个有云的采样点还要走 8 步阳光步进。台风走的是**完整**台风密度（`cloudDensityLite(..., true)`）。进云时还有 8 步表面细化。

**消融证据**（页面内改 march 源码，d3d11，01:52–01:57，同一轮内对照，base 和 base2 相差 ≤1.5%）：

| 变体 | storm-day 云步进 | typhoon-eye | typhoon-bands |
| --- | ---: | ---: | ---: |
| 基线 | 5.96 / 6.10 | 7.43 | 7.69 / 7.60 |
| 主步进里去掉雷暴 / 台风密度（只剩层状云） | **0.66** | — | **0.56** |
| 步长 ×1.5（`t·0.008 → t·0.012`，上限 2 → 3 km） | 3.98（−35%） | — | 6.63（−13%） |
| 空白处步长 2dt → 4dt | 4.82（−21%） | — | 6.31（−17%） |
| 阳光步进 8 → 4 步 | 5.63（−6%） | 6.80（−9%） | 6.43（−16%） |
| 台风的阳光步进 j ≥ 2 改用解析大形 | 5.97（0） | 7.03（−5%） | 6.90（−10%） |
| 关掉表面细化 | 5.16（−13%） | 7.43（0） | 7.34（−5%） |

**结论**：约 5.3–7.1 ms 花在**主步进里逐步求值的雷暴 / 台风密度**上；阳光步进和表面细化只占 5–16%。只动阳光步进救不了。真正的杠杆是**少求值几次复杂密度**：跳过空白区域，或者先查一张粗的占据体积。

### 4.3 热点 2：机翼 pass（可见时 0.65–0.96 ms），其中边缘超采样 0.30–0.47 ms

消融（d3d11，01:26–01:30；`uWingEdgeAA` / `uWingShadowSteps` / `uWingSteps` 都是 uniform，不用重编）：

| 场景 | 基线 | 关边缘超采样（=0） | 只判断不采样（=3） | 自阴影 0 步 | 步数 128 → 64 |
| --- | ---: | ---: | ---: | ---: | ---: |
| noon-cumulus | 0.70 / 0.72 | 0.39（−0.32） | 0.39 | 0.70 | 0.60 |
| sunset-wing | 0.66 / 0.65 | 0.36（−0.29） | 0.36 | 0.67 | 0.54 |
| in-cloud | 0.94 / 0.95 | 0.47（−0.47） | 0.48 | 0.96 | 0.76 |
| night-city | 0.81 / 0.80 | 0.44（−0.38） | 0.39 | 0.80 | 0.65 |
| route-hnd-cts | 0.69 / 0.70 | 0.38（−0.31） | 0.38 | 0.70 | 0.60 |

边缘像素占比（把触发超采样的像素标成色标，从机翼 pass 的 HDR 目标读回计数，`tmp/perf/edge-count.mjs`）：

| 场景 | 边缘像素 | 占全屏 | 占机翼像素 | 含边缘的 8×4 块（≈ 一个 warp）占有机翼的块 |
| --- | ---: | ---: | ---: | ---: |
| noon-cumulus | 3359 | 0.17% | 2.9% | 13.9% |
| sunset-wing | 3428 | 0.18% | 3.0% | 14.4% |
| in-cloud | 8320 | 0.43% | 3.8% | 15.0% |
| night-city | 3847 | 0.20% | 2.8% | 12.8% |

**为什么低效**：0.3 ms / 3400 像素 ≈ **每个边缘像素约 90–140 ns，普通机翼像素只要约 3 ns**，贵了三十多倍。
- 「只判断不采样」（=3）和「关掉」（=0）一样快，说明判断本身几乎不花钱，钱全花在 4 条子射线上。
- 每条子射线都是一次完整的 `wingTrace`：从中心命中距离的**一半**（`t0 = w.t * 0.5`）开始，重新走最多 64 步，也就是把「从半路到机翼」这段空气又走了 4 遍。然后每条子射线还要调一次完整的 `shadeWing`（`wingSurface` 的接缝、铆钉、fbm），也是 4 遍。
- 这 3% 的像素分散在 13–15% 的 warp 里，同一个 warp 的其余 31 条 lane 都要陪着等。

自阴影（0 步）没有收益；步数减半（128 → 64）能省 0.10–0.18 ms，但要核对掠射角的轮廓。

### 4.4 热点 3：场景 pass（0.84–1.09 ms，所有场景都要付）

它不是最贵的，但所有场景都要付，而且是 SC-5 正在拆的对象，所以单独说一下。

- **钱花在窗外，不在舱内**（vulkan 消融，只看相对变化）：`view = outsideRadiance(...)` 换成常量后，night-city 的场景 pass 从 0.99 降到 **0.25 ms**。反过来只保留窗外（舱壁、座椅、内衬、遮光板都换成常量），仍有 0.75–0.88 ms。舱内所有表面加起来约 0.1–0.25 ms。
- **遮光板全放下时窗外照算**：shade=1 时场景 pass 仍是 0.87 ms（`outsideRadiance` 只看 `inBezel && isMain`，不看遮光板），云步进也照走（0.35–0.84 ms，march 只按 `paneDistance` 剔除）。
- 视角（noon-cumulus / night-city，ms）：

  | 视角 | 场景 pass | 机翼 | 云步进 | 合计 |
  | --- | ---: | ---: | ---: | ---: |
  | seated | 0.83 / 0.88 | 0.60 / 0.66 | 0.24 / 0.58 | 1.97 / 2.41 |
  | close（贴窗） | 0.83 / 0.88 | **1.05 / 1.02** | 0.46 / 1.05 | 2.64 / 3.22 |
  | wing（看机翼） | **1.08 / 1.09** | **1.08 / 1.00** | 0.39 / 0.75 | 2.85 / 3.12 |
  | ahead（看前方，座椅占画面多） | 0.92 / 0.93 | 0.42 / 0.42 | 0.17 / 0.42 | 1.79 / 2.05 |
  | behind | 0.93 / 0.99 | — | 0.16 / 0.43 | 1.42 / 1.77 |

  **T06 的「座椅视角 +13–17%」**：对应这里的 ahead，场景 pass 只多 0.05–0.09 ms（+6–10%）。当时的百分比基数是更小的整帧，绝对值很小，**建议关闭这条条件**。「看机翼」视角场景 pass +0.25 ms，原因是视野里海面像素多，海面比天空贵。机翼 pass 在贴窗 / 看机翼时到 1.0–1.08 ms，因为机翼占的像素多了。

### 4.5 其他观察

- 地面场景（fuji-day / night-city）的 `benchFrame` 墙钟（3.7 / 4.2 ms）比 GPU 各 pass 之和（1.65 / 2.85 ms）高 1.4–2 ms。稳态复测时每帧**没有**纹理上传（`tmp/perf/uploads.mjs`），JS 自身每帧约 0.3 ms，native 调用约 0.6 ms（CPU 剖析，`tmp/perf/cpu-profile.mjs`）。所以差额多半来自首轮测量时瓦片还在流式上传。**建议稳态预算按 GPU 之和算**；「瓦片流式加载时的卡顿」另外测，需要在 `ground.pending > 0` 时计时。
- 每帧有 **107 次 `gl.clear`**（three.js 的 autoClear：每个 LUT 切片、FFT 蝶形、每个全屏 pass 都先清一遍），另有 1 次 `generateMipmap`（海浪纹理，正常）。全屏 pass 马上会覆盖整张目标，清屏是浪费，但总量估计 < 0.1 ms，优先级低。

## 七、开发体验反馈

- **哪里慢**：一共约 50 分钟。最慢的是 d3d11 真冷启动（每次 27–40 s，连跑了 5 次），以及页面内替换着色器源码后的同步重编：march 约 5 s 再加 5 s 的 MRT 重编，机翼约 6 s。**最大的风险是 GPU 争用**：01:31 以后 GPU 占用在 18–99% 之间跳，01:57 以后基本一直满载，所以按任务要求把 GPU 测量都压在了前 45 分钟。
- **哪里卡**：
  - `dev-browser bench` 只给整帧数字，给不出按 pass 的分解。它报的整帧 timer 包含 CPU 喂不饱时的 GPU 空闲，in-cloud 3.85 ms、fuji 3.05 ms 都比各 pass 之和高，容易误读。**建议把 `passes.mjs` 收编成 `dev-browser passes` 子命令**，每个 draw 包一个 query，按 uniform 签名自动打标签，已验证可用。
  - `window.__voyage` 没有暴露 `renderer`：拿不到 `readRenderTargetPixels`，也关不了 `debug.checkShaderErrors`。云的 `marchMat` / `resolveMat` 只能读 TS 的 private 字段。建议暴露 `renderer`，并给 Clouds 加正式的材质访问口（SC-4 也提过）。
  - vulkan 后端的 timer query 读数抖动很大（同一变体下机翼 1.3–3.7 ms），**不能用来测性能**，只能测相对趋势。README 的「ANGLE 后端切换」一节可以补一句。
  - 显存：本机其他程序（Fusion 360 等）常驻约 28.8 GB，只剩约 3.7 GB。4K 测量会因为换页而失真，而且不报错。建议 `dev-browser` 启动时打印 `nvidia-smi` 的占用与剩余显存，剩余不足 4 GB 时给出警告。
  - 写复现页时两次掉进「draw 被 WebGL 校验静默拒绝」的坑（sampler 单元冲突、反馈环），看起来就像「不卡」。**复现脚本必须检查 `getError()`**，值得写进 README 坑点。
  - Windows 上 Python 写 JSON 不指定 `encoding="utf8"` 时，中文变体名会按 GBK 写出，Node 读进来就是乱码（已绕过）。
  - `shader-budget.mjs` 在开发服务器运行时会打印 `WebSocket server error: Port 24678 is already in use`（vite HMR 端口冲突），不影响结果，但容易让人以为出错了。
- **怎么绕过的**：自己写了 `tmp/perf/` 下的一组脚本（§6）；用 d3d11 做所有 GPU 计时，vulkan 只用在不看绝对值的场景消融上；每次测量都记下 GPU 占用。
- **希望有**：`dev-browser passes`（按 pass 计时 + 变体消融）、`dev-browser stall`（冷启动逐调用计时，SC-4 那种「卡在哪」的问题三次运行就能定位）、`__voyage.renderer`。
