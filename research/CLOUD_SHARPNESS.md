# 云的锐利度研究（CLOUD_SHARPNESS）

- 课题：用户原话「目前的云感觉整体看来氛围感很好，但是感觉不够锐利，就是没有微软模拟飞行中那种云朵锐利的感觉，以及光影打在云朵上那种边缘的高光的那种高分辨率的质感。这方面我们是缺了什么吗？」
- 日期：2026-09-27；研究代理；基于主分支 `ebb5f03`→`6900fd6`（期间 master 合并了 TR07 火车声音，不涉及 `src/clouds/*`）。
- 方法：不改 `src/`。所有对照都在同一页面、同一冻结姿态下完成：在页面内替换云步进片段（`clouds.marchMat`），然后原地重新累积。脚本和原始数据见文末「复现」。
- 结论的可信度：每个数字都是在 1600×1200、DPR 1、headless Chrome（ANGLE Vulkan，画面与 d3d11 一致，见 README）下测的。同一版代码跑两次，「收敛参考帧」逐位一致（static 与 static2 的所有指标都相同），所以指标噪声底为 0。GPU 计时是在别的代理也在用机器时测的，只能看量级。

## 结论先行

**「糊」主要不在分辨率上，而在明暗对比上。** 默认档下云步进本来就是全分辨率（云缓冲 1600×1200，和屏幕 1:1，没有上采样）。以强边缘的 10–90% 上升宽度计，收敛后的云边只有 2.0–3.0 px，这不是「糊」。

MSFS 那种「锐」主要来自三件事，我们都缺：

1. **云体内部的受光 / 背光对比太低（最大缺口）**：云芯（不透明度 > 0.97）内，5–95 分位的亮度差只有均值的 ±6%（noon-cumulus `int_rng` 0.118）。根因是多次散射的八度近似：`b *= 0.35`、`a` 衰减 0.62、6 阶，**违反 Wrenninge 近似「散射衰减 a ≤ 消光衰减 b」的能量守恒约束**。高阶散射几乎不衰减地灌满背光面，受光面和背光面被抹平，菜花状隆起读不出来。只留 2 阶（`ms2`）时 `int_rng` 升到 0.26（+120%），clouds-variety 从 0.44 升到 0.77，帧时间不变。
2. **曝光把整片白云压成中灰**：云占满窗时，自动曝光按窗外对数均值取中灰 0.18，受光最亮的 1% 云像素在显示上只有 157–163/255（clouds-variety、cu-side 的 `yp99`）。没有高光，也就没有「高分辨率的亮边」。+0.5 EV 时 `yp99` 升到 172–178。T12 当年把多次散射加到 6 阶、放慢衰减，就是为了补「顺光的云偏灰」，相当于用不守恒的散射去补曝光的问题。两件事要一起改。
3. **轮廓的软化来自沿视线的步长，不是屏幕分辨率**：步长 = 距离 × 0.008，约等于 10 个像素足迹。掠射的云顶和薄边被抖动后的大步长平均成半透明的毛边。步长减半而 mip 不变（`halfStepKeepLod`）时，不透明度边宽减小 20–27%（2.6→1.9 px、2.7→2.1 px、5.3→4.2 px）；backlit 近处云底的水平「梳齿」横纹也明显变少。代价是全程半步长让云步进 +75%，所以要做成「只在进云处细化」（雷暴已经有这段代码）。

次要因素（各贡献 0.1–0.4 px，或只在特定条件下出现）：

- 时间累积在运动中抹软边缘：+0.1–0.4 px（+3–15%），运动时边缘还会漏出单帧的棋盘状抖动噪点。
- 画质档降到「中」（云 0.75）后按双线性上采样：高频能量 −30–45%。
- 细节噪声的 mip 比像素足迹粗约 1.4 级：高频能量少 7–30%。
- bloom / 眩光：约 0.1–0.2 px。
- 粉末效应：顺光时略压暗云边。

**银边**：逆光场景里，云边（不透明度 0.2–0.8）只比云芯亮 15%（`rim` 1.15，p90 1.34）。`ms2` 下是 1.20。银边弱，和第 1、2 条是同一个问题：背景太亮、曝光太平，前向峰被「灌满」的云芯稀释了。

**前 3 条建议**（详见 §3）：

- **C01**：多次散射改成能量守恒、少阶。零帧时间，冷编译不增反减。主要作用是让云体明暗对比 ×1.5–2。
- **C02**：窗外以云为主时抬高曝光的目标中灰，外加一点色调映射对比。零帧时间。作用是让受光云顶回到高光区。C01 和 C02 必须成对合并。
- **C03**：层状云进云处表面细化（沿用雷暴已有的 refine 段），预计云步进 +15–30%（待测）。作用是让轮廓边宽 −20% 左右，同时去掉掠射横纹。

## 1. 诊断：「糊」从哪来（逐项量化）

### 1.1 测量方法

对每个场景，先正常飞 1.5 s，再冻结（`__voyage.freeze(true)`），得到以下几种图：

| 名字 | 含义 |
| --- | --- |
| `inflight` | 冻结那一刻的真实缓冲（带运动的时间累积，混合 0.12 + 3×3 min/max 夹取），也就是用户看到的样子 |
| `staticTaa` | 同一姿态、零运动，用原版 resolve 累积 64 帧 |
| `static` | 同一姿态，resolve 临时改成「第 i 帧权重 1/(i+1)、不夹取」的真平均 64 帧（抖动相位 `uFrame % 64` 走满一圈），得到「收敛参考」 |
| `single` | 只画 1 帧、不累积 |
| 变体 | 页面内替换 `clouds.marchMat` 的片段，编译好后按 `static` 的方法累积 |
| `medium075`、`noGlare`、`ev+0.5` | 不改云步进，只改画质档 / 眩光混合 / 曝光补偿 |

指标（`tmp/cloud-sharp/csharp_metrics.py`）：

- `w1090`：在 `static` 截图上挑 400 个最强边缘点，沿梯度方向取剖面，量 10%→90% 的上升宽度（px），取中位数。`op_w1090` 是在云缓冲的不透明度（1 − T）上做同样的计算，不受色调映射影响。
- `hf`：高频能量比 E|I − G₁I|² / E|I − G₄I|²（只统计云像素）。注意：残留的时间累积噪声也会算进 hf，所以只在同为「收敛」的图之间比较。
- `int_rng`：云芯（不透明度 > 0.97 且腐蚀过）内亮度的 (p95 − p5) / 均值，是「明暗对比」的指标。`int_c` 是云芯内去掉 σ=3 低频后的标准差 / 均值。
- `rim`：云边（不透明度 0.2–0.8）的平均亮度 / 云芯平均亮度。`yp99`：云像素显示亮度的 99 分位（0–255）。
- `op_mean`、`op_corr`：不透明度均值，以及和 `static` 的相关系数（用来看云的形状 / 大小有没有变）。

场景：

- `noon-cumulus`：10.7 km 俯看积云，太阳 58°。
- `sunset-wing`：黄昏，太阳 1.7°。
- `clouds-variety`：5 km、云量 0.62、太阳 31°。
- `cu-side`：4.5 km 在浓积云层里平视（近景）。
- `backlit-cu`：4 km、太阳 10° 在窗内，逆光。

### 1.3 云步进分辨率与上采样

- 画质档：高 = ×1（默认）/ 中 ×0.75 / 低 ×0.5 / 最低 ×0.5 + DPR 上限 1.0（`src/quality.ts:30-35`）。默认高档下云缓冲与画布 1:1。窗外 pass 用 `cloudBufferColor(uClouds, gl_FragCoord.xy / uResolution)` 取样，正好落在纹素中心，**默认档没有上采样误差**。
- 降到 0.75 时是普通双线性上采样（没有深度 / 透射率感知）：hf −30–45%，边宽 +0.2–0.4 px（`medium075` 列）。
- **自动档会降**：本次前两轮 headless 运行里，`applyScene` 刚切完场景时自动档读数分别是「自动 → 低（GPU 3.0 / 预算 11.7 ms）」和「→ 中」。原因是切场景瞬间地面瓦片、云影图、占据网格重建造成的尖峰。升档要连续 3 s 低于预算的 55%，再加 1.5 s 冷却，所以要过几秒才回到高。安静时单独开页面观察 25 s，一直在「高」（`tmp/cloud-sharp/csharp-autotier.mjs`）。**在用户更弱的 GPU 上，很可能长期停在中 / 低档**。
- **高分屏**：`dprCap = 1.5`。DPR 2 的屏幕（Mac Retina）上，整张画布按 1.5 倍渲染，再由浏览器放大 1.33 倍：整幅画面（不只是云）都被双线性放大一次，量级和上面的 0.75 相当。本机无法复现用户的机器，**需要问用户面板「画质」一行显示的是哪一档、屏幕 DPR 是多少**。

### 1.4 时间累积与重投影

- resolve（`clouds.ts` RESOLVE_FRAG）：历史权重 0.88，3×3 min/max 夹取；历史用双线性 `texture()` 取样；抖动只沿视线方向（IGN × 黄金比例，64 帧一圈），**没有屏幕空间的亚像素抖动**。
- 单帧噪声极大（`single` 的 hf 是 0.65，截图里是棋盘点阵），全靠时间累积抹平。
- 零运动时，原版累积（`staticTaa`）比真平均多一些残留噪声（hf +12–50%），边宽相当。
- 运动时（`inflight`，rAF 6.6–12 ms）边宽 +0.1–0.4 px。第一轮在 rAF 25 ms 下，noon 是 2.6→3.0 px（+15%），帧越慢、每帧位移越大，抹得越软：
  - 双线性重采样历史，每帧引入 f(1 − f) px² 的方差，稳态累积约 7 f(1 − f)；f = 0.5 时 σ 约 1.3 px。
  - 3×3 min/max 在云边上本来就同时含云和天空，夹取几乎不起作用，挡不住这种软化。
- 运动时云边还会漏出单帧棋盘噪点（`sunset-wing/g-taa.png` 左上）。这是锯齿 / 闪烁类的缺陷，**比「软」更违反铁律**。

### 1.5 步长、抖动、噪声频率与 mip

- 步长 `dtBase = clamp(t·0.008, 0.06, 2.0)` km；空白处 2 倍步长。1600×1200 下像素足迹约 t × 0.00078，所以**一步 ≈ 10 个像素足迹**。只有雷暴 / 台风进云时才做「退回最近空白点 + 8 小步」的表面细化（`refineOn = nearW.x`），层状云没有。
  - 掠射的云顶、薄边、云底，其消光区间比一步还短。抖动后命中与否按概率平均，结果是半透明的毛边，外加掠射处的水平横纹（backlit 近处云底的「梳齿」）。
  - `halfStepKeepLod`（步长减半、mip 不变）：不透明度边宽 −20–27%，形状相关 0.98–0.99，云略大（不透明度均值 +3–14%，说明现在的大步长在系统性地漏掉薄边）。
- 噪声：形状 128³ 覆盖 7 km（纹素 55 m），细节 64³ 覆盖 0.9 km（纹素 14 m，T32 的六边形随机平铺）。mip 按**步长**选：`lod = log2(dtBase / 0.055)`，形状和细节用同一个 lod。
  - 形状噪声实际滤波尺度约 10 px，细节约 2.6 px。
  - `lodDetail`（细节 mip 降 1.37 级，约 1 纹素 / 像素）：hf +7–30%，边缘多了细碎絮边，边宽反而 +0.1–0.3 px（细节变成亚像素级的半透明毛边）。
  - `lodPix`（形状也按像素足迹）：云变大（不透明度均值 +3–17%，相关 0.96），更蓬松，边宽 +0.3–1.4 px。**不是锐化**，还会带来远近云量的偏差：mip 越粗，remap 阈值后云越小。这本身也值得记一笔：mip 选择会系统性地改变云量（远处的云被「按距离侵蚀」）。
  - 结论：mip 不是主要的糊源，按像素足迹整体降 mip 不划算。只把细节降约 1 级有「纹理感」收益，但要按铁律做闪烁测试。
- 近处（cu-side，云就在机翼旁边）不透明度边宽 5.3 px，是所有场景里最软的。这是细节噪声最细 14 m 纹素的物理上限：几公里内一个纹素就占好几个像素，被双线性放大。

### 1.6 受光、相函数、粉末、多次散射

- 受光步进：6 步，60 m 起每步 ×1.9（约 3.1 km），前 3 步带细节，lod + 0.5。
  - `lightSharp`（6 步都带细节、lod 不 +0.5）：hf +2–9%，int_rng ±3%，收益小。
- **多次散射**（`clouds.ts` 363–371 行）：`sunScatter += a·phase·exp(−b·od)`，每阶 `a *= 0.62`（雷暴 0.7）、`b *= 0.35`、`c *= 0.5`，共 6 阶。
  - Wrenninge 2013 的近似要求**散射衰减 a ≤ 消光衰减 b** 才守恒；Hillaire 在 Frostbite 里沿用这条约束，常用 a = b = c = 0.5。我们 a = 0.62 > b = 0.35。
  - 各阶权重之和 2.48，od = 5 时高阶合计是单次散射的约 100 倍：背光面被高阶散射「灌满」。
  - 这就是 int_rng 只有 ±6% 的根因：`ambHalf`（环境光减半）几乎不改变 int_rng（0.118→0.122），`ms05`（b 改 0.5）+52%，`ms2`（只留 2 阶）+120%。
- 前向峰（T12）：`0.6·hg(cosT, 0.9)·exp(−0.25·od)` 是对的方向。但逆光时 rim 只有 1.15，因为同一处云芯也被高阶散射提亮了，边缘相对不突出。
- 粉末（Beer-Powder，只在非逆光时起作用）：`noPowder` 在 noon / cu-side 让 int_c +5–28%、整体 +2–5/255。顺光时粉末把云边压暗，和 MSFS 的亮边正好相反。量不大，放进 C01 一起调。

### 1.7 曝光、色调映射、bloom

- 自动曝光：窗外中心加权的对数均值 → 目标中灰 0.18（`exposure.ts` 的 `exposureKey`）。只有「均匀视野」（云中 / 雪原，线性均值 ≈ 对数均值）才加 `uSnowEv = 2`；**有空隙的云海不满足这个判据**。于是满窗的受光云被按「中灰」曝光：clouds-variety 云像素均值 142/255、99 分位只有 163/255，cu-side 是 139 / 157。
- AgX（three 默认版）在中间调的斜率偏缓，进一步压缩云体的明暗差。「+0.5 EV」对照说明：只要曝光往上走，云就进入高光区。至于要不要换成更「出片」的 AgX 变体（punchy / 提高对比），交给美术总监判断。
- bloom / 眩光（混合 4%）：`noGlare` 让边宽 −0.1–0.2 px、hf +2%。影响小，**不建议为锐度去动它**（它负责太阳和高光的真实感）。

从这些资料里能归纳出业界拿到锐利边缘与高光的手段，逐条对照我们的现状：

1. **近表面小步长**（雷暴 refine、Nubis³ 的 SDF 步进、UE 的采样数缩放）。我们只给雷暴 / 台风做了，层状云没有。→ C03。
2. **多次散射阶数少、守恒**（UE 最多 2 阶，a ≤ b）。我们是 6 阶且不守恒。→ C01。
3. **曝光让受光云进入高光**：各家都没有明写，但 UE / MSFS 用的都是物理曝光 + filmic 曲线，白天窗外的 EV 基本固定，不会因为「满屏都是云」就把云压成中灰（推测）。→ C02。
4. **时间重建里保住边缘**（邻域方差夹取、Catmull-Rom 取历史、按深度 / 透射率拒绝历史）。这是 TAA 的通用做法，不是云专有的。→ C05。
5. **细节在近处继续加频率**（HZD 的 curl 扰动、Nubis³ 的 up-rez）。→ C06（近景）。
6. 按屏幕导数选细节 LOD：各家都有，但我们实测「全部按像素足迹」并不更锐（1.5 节）。只对细节降约 1 级有纹理收益。→ C04。

## 3. 改进方案与任务清单

排序按「对锐度 / 质感的贡献 × 代价」。所有改动都在云步进的公共主体里（层状云受光段、步进循环、resolve、曝光），**不新增 uniform 分支**（W00 / T12 坑）。PERF-10 按天气拆出的每个变体都会带上这些改动，彼此兼容；C03 只放宽层状云的 refine 条件，**不许把雷暴代码带进晴天变体**。

### C01 多次散射改为能量守恒、少阶（最高）

- **做法**：`b` 衰减 ≥ `a`（例如 a = 0.5、b = 0.5、c = 0.5），阶数 6 → 2–3（循环常量上界，FXC 展开份数减少）。雷暴另取一组（光学厚度几百，确实需要更多高阶，可以 3 阶，a = b = 0.6），同样守恒。损失的整体亮度不要用「多加阶」补，交给 C02；如仍偏暗，再按「厚云有效反照率 0.7–0.8」标定一个与光学厚度无关的**常数**反照率系数。粉末效应（顺光时压暗云边）一起重新调，可以只在凹处 / 受光面背面保留，或按 Nubis 的「dark edges」思路只作用在朝向观察者的薄边。
- **预计改善**：int_rng / int_c ×1.5–2.2（ms05：+33–52%，ms2：+60–120%）；backlit 的 rim 1.15 → 1.20。
- **代价**：云步进帧时间 0（实测 noon 0.40→0.41–0.42 ms、variety 1.07→1.08–1.09 ms，在噪声内）；冷编译预计持平或略降（循环份数变少），要用 `shader-budget --only cloud-march` 实测。
- **风险**：整体变暗 7–20%（ms2 下 ymean −9 / −20 / −29），要和 C02 同批。T12 的「顺光偏灰」会回来，这就是依赖 C02 的原因。雷暴、台风的塔身明暗要美术总监复看（T38 / T44 的圆桶、拱洞问题和环境光有关，这次不动环境光）。
- **依赖**：C02。与 PERF-10 同文件（`clouds.ts` 步进段），等 PERF-10 合并后再开工，或交给同一个代理。

### C02 以云为主的窗外曝光：抬高目标中灰（最高，与 C01 成对）

- **做法**：把 `uSnowEv` 的判据从「均匀视野」扩展到「窗外以受光云为主」，例如用窗外线性均值与对数均值之差加上窗外高亮像素比例判断；或者对白天的窗外改用「物理 EV 锚定 + 有限自适应」（sunny-16：白天窗外 EV100 约 15–16，自适应幅度 ±1.5 EV）。色调映射保持 AgX，美术总监可以评估是否用 punchy 版或提高中间调对比。
- **预计改善**：满窗云场景 `yp99` 157–163 → 175–200（+0.5 EV 实测 +15/255；目标约 +1 EV）。受光云顶进入高光区，边缘前向峰才有空间「比云芯亮」。
- **代价**：帧时间 0；曝光程序很小，冷编译可以忽略（不在关键路径）。
- **风险**：全局性的，海面 / 天空 / 舱内（T23 双区曝光、T30 倒影上限）都会跟着变，必须走美术总监审查和全量回归。黄昏 / 夜景不要动（判据限定在白天明视）。
- **依赖**：无；和 C01 同批合并。

### C03 层状云进云处表面细化（高）

- **做法**：把现有「从空白进入云时退回最近空白点、8 小步重走」（`refineOn` 目前只在 `nearW.x` 时开）放开给层状云。进云时步长降到约 2–3 px 足迹，走完一小段再恢复。雷暴那段代码已经处理过 T03 / T04 的等高线、漏检坑，照搬它的「退回最近空白采样点」逻辑。层状云的 192 步上限要核对：会不会在远处用完（T33 纱窗点阵）。
- **预计改善**：不透明度边宽 −20–27%、亮度边宽 −0.3–0.5 px（`halfStepKeepLod` 是上限估计）；backlit 近处掠射横纹减少；薄边不再被系统性漏掉（不透明度均值 +3–14%，要按场景复核云量是否偏大）。
- **代价**：`halfStepKeepLod` 是全程半步，云步进 +74–78%（noon 0.40→0.70 ms、variety 1.10→1.93 ms），这是上限。只在进云的那一段细化，预计 +15–30%，**必须实测**。冷编译：refine 代码本来就在同一个循环里，只改条件，预计很小；但 W00 / T12 的教训是「改一处可能掉进慢一档」，要 `passes.mjs --variants` 逐项撤回确认。
- **风险**：细化位置随抖动变，会不会在薄云上产生新的点阵 / 闪烁？用 `dev-browser.mjs flicker` 在 noon-cumulus、clouds-variety、backlit 上测块能量 CV 和爬行指标。
- **依赖**：PERF-10 之后（同一段循环）。

### C04 细节噪声 mip 降约 1 级（中）

- **做法**：细节噪声的 lod 与形状分开：`lodDetail = lod − 1.4`（≈ 1 纹素 / 像素足迹）。形状噪声维持按步长选（实测按像素选会让云变大变蓬，不更锐）。
- **预计改善**：hf +7–30%（云面上的絮状纹理更细），边宽基本不变或略宽。
- **代价**：云步进 +7–22%（noon 0.40→0.49、variety 1.10→1.16 ms），远处样本读更细的 mip，缓存更不友好。冷编译 0。
- **风险**：**闪烁**（README：远处的云必须用 mip，否则严重闪烁）。只在 `flicker` 的块能量 CV / 爬行指标不升的前提下合并；如果 150 km 附近出现闪点，按距离把这 1.4 级渐变回 0。
- **依赖**：无；建议在 C01 / C02 之后做，那时纹理才看得出来。

### C05 时间累积保边（中）

- **做法**（逐项加，逐项测）：
  1. 历史取样用 5-tap Catmull-Rom（双线性重采样的累积软化大约是 σ 1 px 量级）；
  2. 邻域夹取改为 YCoCg 方差夹取（μ ± 1σ），对透射率单独夹；
  3. 运动中按像素位移适当提高当前帧权重（位移大时 0.12 → 0.2），但要防噪点。
- **预计改善**：运动中的边宽回到静止值（−0.1–0.4 px），运动时漏出的棋盘点阵减少（铁律：闪烁 > 软）。
- **代价**：resolve 现在 0.11–0.12 ms，已超预算 0.05（PERF-11 正在压）。Catmull-Rom 取历史约 +0.02–0.04 ms，**要和 PERF-11 协调**：只对左半颜色做，右半深度仍用双线性。冷编译很小。
- **风险**：方差夹取夹得太紧，远处的薄云会闪。
- **依赖**：PERF-11 之后。

### C06 近景细节（低空、云就在机翼旁时）（中低）

- **做法**：离相机 < 约 8 km、像素足迹 < 14 m（细节纹素）时，叠加一级 4 倍频的细节（或 HZD 式的 curl 扰动），权重随距离淡出。只作用在侵蚀阈值附近（云边），云芯不取。
- **预计改善**：cu-side 不透明度边宽 5.3 px →（估计）3–4 px。
- **代价**：多一次 3D 纹理取样（六边形平铺是 2–3 个样本；可以只取权重最大的一个格点，T32 的做法），估计云步进 +10–15%。冷编译要实测。
- **风险**：近处的规则感和平铺感（T32），需要自相关检查。
- **依赖**：C04。

### C07 画质自动档与高分屏（低成本，先做信息收集）

- **做法**：
  1. 先问用户：面板「画质」一行显示什么、屏幕 DPR 是多少；
  2. 自动档降档时优先降别的（例如地面细节变体、bloom 级数），云分辨率放在最后；
  3. 云分辨率 < 1 时，上采样改为按透射率 / 深度感知的联合双边上采样，或 Catmull-Rom；
  4. 切场景 / 重建云影图时的尖峰不计入降档（加一个「重建中」的豁免窗口）。
- **预计改善**：避免 hf −30–45% 的整体软化。
- **代价**：上采样放在窗外程序里会动到窗外 sampler 和冷编译，放在 resolve 里只多一次取样。
- **依赖**：C05（同在 resolve）。

### C08 受光步进细节（低）

- `lightSharp`：hf +2–9%，云步进 +3–5%。收益小，等 C01 之后再评估（C01 之后受光结构更可见，可能值得）。

### 不建议做的

- 形状噪声整体按像素足迹降 mip（`lodPix`）：云变大、变蓬松、边更宽，还会带来远近云量偏差。
- 为了锐度去关 bloom / 眩光：收益 0.1–0.2 px，损失太阳和高光的真实感。

## 开发体验反馈

1. **缺一个「收敛参考帧」工具**。这次最有用的一招，是在页面内给 resolve 临时加 `uCsBlend` / `uCsClamp`，按 1/(i+1) 真平均 64 帧（抖动相位走满一圈）。结果逐位可复现，噪声底为 0，比「冻结后截图」干净得多：冻结只是复用最后一帧的缓冲，里面还带着 0.12 混合的残留噪声，hf 会差 12–50%。建议给 `probe.mjs` 加 `--converge N`，并在 `clouds.ts` 里留一个调试用的混合权重覆盖（不改默认程序文本的前提下，可以放在 resolve 的 uniform 里）。
2. **跨运行的截图位置不一致**：每次 `applyScene` 后正常飞 1.5 s，飞机位置差几十米，旧变体截图和新 static 就对不上了（我一度以为补丁改了云的形状）。现在的做法是每次都整套重跑，并用不透明度相关系数 `op_corr` 做核对。建议 `applyScene` 支持 `freezeAfter: true`（场景摆好立刻冻结）。
3. `passes.mjs --variants` 跑第二个场景时会报「程序缓存数没有增加」。原因是前一个场景已经编过同一份变体源码，不是真问题，但提示容易误导。建议改成「源码哈希已在缓存中」时不报。
4. 主分支 dev server 在别的任务合并时会热更新，页面整页重载，我的一轮测量因此中断（`__cs` 丢失）。长测量最好用自己起的 vite，或者 dev-browser 检测到 HMR 重载时明确报错。
5. `compare.mjs --crop` 只能横排，8 张以上就看不清。这次写了 `tmp/cloud-sharp/csharp_grid.py`（网格 + 标签），建议给 `compare.mjs` 加 `--cols N`。
